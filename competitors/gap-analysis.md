# HoBo vs competitors — gap analysis

> A cross-competitor synthesis: where HoBo's [design suite](../docs/design/README.md) (Plans 0–36) leads, matches, or **falls short** of [Aspire](./aspire/README.md), [Nitric](./nitric/README.md), [Humanitec](./humanitec/README.md), [Convex](./convex/README.md), and [shoo.dev](./shoo/README.md). Produced with the [Superpowers](../docs/agent-tooling.md) methodology — **brainstorm → compare → review → iterate**. Companion to each folder's `differentiators.md` (their strengths) and `hobo-mapping.md` (per-feature parity ✅ has / ➕ adds / 🔜 planned).
>
> **Bottom line (updated 2026-06-22):** the original analysis found the architecture broad with most gaps *tracked* as open questions, one true blind spot (**reactive / live-query**, now Plan 32/ADR-0029), and two designed-but-shallow surfaces (**Forge generation**, **search/ingress**). **All of those — and every tracked open question — are now remediated in design** (gaps G1–G8 + open questions #3/#10/#15–20/#22–23, via Plans 32–36 + ADRs 0029–0043). The sections below record the original findings with their ✅ closures inline.

## 2. Brainstorm — sharp questions that surface the gaps
*(Superpowers `brainstorming` style: challenge the design's assumptions, one pointed question each.)*

> **Historical framing — all resolved.** The questions below were the *open* probes at analysis time; each is now answered in design (see the ✅ closures in §3 and the ADR/Plan links). They're preserved as the reasoning trail, not as current open items.

1. **Reactivity:** HoBo has a `Streamer` port and an event log — but a Convex user gets `useQuery()` that re-runs and pushes to every client on write, with consistent snapshots. *What is HoBo's client-facing live-query story?* Is it "bring your own websocket over `Streamer`", or a first-class reactive-query model with cache-invalidation + consistency guarantees? Today: **undefined.**
2. **Forge depth:** Plans 6/23 say Forge *generates* providers/impls and gates them by conformance. *But what actually generates them?* The conformance gate ([09](../docs/design/09-verification-open-questions.md)) is specified; the generation loop (inputs, prompt/program synthesis, repair iteration, the training-engine for impls) is thin outside [Plan 23](../docs/design/23-stubbable-ai-implementations.md)'s `use training`. *Is "Forge generates providers" demonstrable, or aspirational?*
3. **Matching credibility:** ✅ **RESOLVED → [ADR-0033](../docs/design/adr/ADR-0033-deterministic-matching-and-planner-selection.md)** ([Q3](../docs/design/09-verification-open-questions.md) + ADR-P4): selection on the deploy path is **deterministic rules** (filter on `require` → rank lexicographically [specificity → `priority` → configurable objective, default min-cost → stable tiebreak] → record full ranking in `match.Decided`); constraint-solvers/LLMs are **advisory only, off-path**. Deterministic + replayable + auditable — the credibility property prod needs, and more transparent than Humanitec's opaque selection.
4. **wasm to prod:** ✅ **RESOLVED → [ADR-0031](../docs/design/adr/ADR-0031-wasm-host-of-record-and-runtime-substrate.md)** ([Q10](../docs/design/09-verification-open-questions.md)): a **`component-host` port** (the host is a property of a Camp), **Wasmtime** locally, **wasm-in-container** as the portable v1 prod default (reuses the OCI pipeline → runs anywhere a container runs), and **SpinKube / wasmCloud-lattice / provider-native** as opt-in per-Camp adapters. "wasm-first" now has a concrete substrate.
5. **Data, not just infra:** ✅ **RESOLVED → [Plan 34](../docs/design/34-app-data-migrations.md)** ([ADR-0032](../docs/design/adr/ADR-0032-data-portability-schema-versioning.md)): declarative-schema + auto-diff migrations, gated **expand/backfill/contract** apply + snapshot rollback, and **export→import within a provider equivalence class** for cross-cloud moves ([Q15](../docs/design/09-verification-open-questions.md); v1 = relational `sql`/Postgres). The multi-cloud promise now covers *data*, not just infra.
6. **Batteries vs Lego:** Convex is one consistent backend; HoBo is ports→providers (compose-it-yourself, per cloud). *Does the agnostic Lego model cost too much first-run DX vs Convex's batteries?* Mitigations: a "starter Resource Pack" + great `hobo dev`.

## 3. Gaps — prioritized
### A. NEW (no existing plan or open question)
- **G1 — Reactive / live-query data model (Convex).** ✅ **CLOSED → [Plan 32](../docs/design/32-reactive-live-queries.md)** ([ADR-0029](../docs/design/adr/ADR-0029-reactive-live-query-model.md)): a `query()`/`"use query"` primitive + event-log **reactor** (hybrid: native projections default, opt-in provider DB **change-feed** capability), **per-query consistent snapshot @ `seq`** + reads-your-writes, client `useQuery()`. Was the one true blind spot; designed via brainstorming + grill-with-docs.
- **G8 — End-user / application auth surface (shoo / Convex Auth / Clerk / Auth0).** ✅ **CLOSED → [Plan 36](../docs/design/36-end-user-auth.md)** ([ADR-0038](../docs/design/adr/ADR-0038-end-user-application-auth.md)): a **federate + verify** `auth()` port (`hobo:auth`) validating OIDC/JWT from any IdP (Google/GitHub/Clerk/Auth0/customJwt) via the existing JWKS machinery + a thin dev built-in; a **unified principal model** (end-user = `PrincipalRef`, `ctx.user`, authz via the same policy plane + `.allow()`, same event audit); **stateless JWKS verify + event-sourced sessions** for revocation; `useAuth()`/`signIn`/`signOut`. *(Identified by the 2026-06-22 re-survey; not in the original analysis.)*
- **G2 — Vector & full-text search surface (Convex).** ✅ **CLOSED → [Plan 35](../docs/design/35-search-vector-surface.md)** ([ADR-0034](../docs/design/adr/ADR-0034-search-vector-surface.md)): a first-class unified **`search` port** (full-text + vector + hybrid/RRF) behind a provider equivalence class (pgvector+PG-FTS ↔ OpenSearch/Azure AI Search/Pinecone), declarative migration-gated indexes, determinism-split reactivity (full-text reactive, vector = step), and a secretless **`embed`** capability (local/hosted, BYO escape hatch). Closes [Q22](../docs/design/09-verification-open-questions.md).

### B. Designed-but-shallow (deepen an existing plan)
- **G3 — Forge *generation* pipeline.** ✅ **CLOSED → [Plan 33](../docs/design/33-forge-generation-pipeline.md)** ([ADR-0030](../docs/design/adr/ADR-0030-forge-generation-inputs-and-algorithm.md)): the **scaffold → LLM-fill → validate(sandboxed, no-egress) → repair(via `training-engine`, bounded) → certify(signed provenance)** loop, **contract-first** inputs (WIT + conformance + Capability Manifest authoritative; docs/OpenAPI sanitized hints), unified across **providers + implementations + Resource Definitions/Packs**. The unique differentiator is now specified end-to-end (was the least-detailed).
- **G4 — Custom domains + ingress depth** (Nitric has custom domains): ✅ **CLOSED → [ADR-0035](../docs/design/adr/ADR-0035-custom-domains-and-multi-cloud-ingress.md)** ([Plan 13](../docs/design/13-networking-connectivity.md) §Custom domains): a first-class **Yard-level `domain`** fronting member Camps, **policy-driven DNS routing** (failover/weighted/latency via a `dns` capability), **ACME DNS-01** secretless certs (provider-managed adapter). HoBo goes beyond single-cloud custom domains to a real **multi-cloud ingress** story. Closes [Q23](../docs/design/09-verification-open-questions.md).
- **G5 — SQL migration DSL** (Nitric `.up.sql`, Humanitec preview): ✅ **CLOSED → [Plan 34](../docs/design/34-app-data-migrations.md)** ([ADR-0032](../docs/design/adr/ADR-0032-data-portability-schema-versioning.md)) — folded into the data-migration work: **declarative desired-schema + auto-diff** (raw `.up.sql`-style SQL is the escape hatch), gated expand/backfill/contract apply + snapshot rollback.
- **G6 — Air-gapped / sovereign mode** (Humanitec): ✅ **CLOSED → [ADR-0036](../docs/design/adr/ADR-0036-air-gapped-sovereign-mode.md)** ([Plan 28](../docs/design/28-relay-gitops-pipelines.md) §Air-gapped): beyond the connected-private HoBo Relay, a first-class **zero-egress Yard profile** — **signed offline bundle import** (same trust boundary), **in-boundary trust roots** (Identity/internal-CA/KMS) + **local models with graceful degradation**, no phone-home, and a capability-degradation matrix. The deterministic core works with no egress. Multi-Yard **federation** stays deferred ([Q20](../docs/design/09-verification-open-questions.md)).
- **G7 — SDK codegen surface** (Aspire/Convex typed end-to-end): ✅ **CLOSED → [ADR-0037](../docs/design/adr/ADR-0037-sdk-codegen-surface.md)** ([Plan 2 §Generated code](../docs/design/02-sdk-api.md)): a **checked-in `_generated/`** directory generated deterministically from WIT interfaces (jco) + Zod + `.allow()` + the bindle graph (typed `ctx.bindings`, `useQuery`/search, workflow/step sigs, `api` tree), run in `hobo dev`/`build` with a **`hobo codegen --check`** CI drift gate + MCP parity. The codegen DX is now shown, not just promised.

## 3b. Re-survey — Dapr & Encore (2026-06-22)
After the backlog closed, two of the closest **un-captured** comparables were added (see [`dapr/`](./dapr/README.md), [`encore/`](./encore/README.md)) and analyzed against HoBo's now-complete design:

- **Dapr** ([`dapr/`](./dapr/README.md)) — the closest *architectural* analog: portable building-block APIs with pluggable components behind them. Its 12 building blocks map **near 1:1** onto HoBo's WIT ports/primitives — strong external **validation** of HoBo's ports/capability-provider spine. Dapr stops at the **runtime/sidecar** layer (it doesn't provision infra, has no control-plane planes, no event-sourced audit, hand-written adapters). **No new major gap** — HoBo is a superset (provisioning + control plane + AI-native) on top of the same runtime model.
- **Encore** ([`encore/`](./encore/README.md)) — the closest *product* analog: infrastructure-from-code for TS/Go → AWS/GCP, with excellent local DX (`encore run` real-infra + `:9400` dashboard + preview envs) and an MCP agent surface. It **validates** HoBo's IfC authoring (Plans 21/22), local-fidelity (ADR-0042), preview-Camps (Plan 26), and MCP (Plan 6). It's bounded to **AWS/GCP + TS/Go + fixed mapping**; HoBo's breadth (multi-cloud + pluggable IaC + language-neutral wasm + Resource Definitions/Matching + event-sourced governance + Forge) is the delta. **No new major gap.**

**Minor candidates surfaced (low priority, not a remediation round):**
- **G9 — first-class app-facing `crypto` capability** (Dapr's *cryptography* building block: encrypt/decrypt/sign with keys the app never holds). HoBo has secrets + envelope encryption ([Plan 12](../docs/design/12-security-multitenancy.md)/[Plan 31](../docs/design/31-config-secretless-secrets.md)) but **not** an explicit app-facing crypto port — a small, additive `hobo:crypto` capability would close it. *Low priority; covered for most cases by secrets+KMS.*
- **Minor — explicit app-facing `lock()` primitive + declarative per-binding resiliency policies** (Dapr exposes distributed-lock + retry/timeout/circuit-breaker config). HoBo *has* the mechanisms (ActorHost lease, [Plan 5](../docs/design/05-reliability-ha.md) circuit-breakers/retries) but not as app-declared surface; exposing them is a small DX add. *Low priority.* **Mostly subsumed:** the common "serialize writes to this entity" case is now the **aggregate boundary** — an aggregate is an actor's single-writer lease ([ADR-0053](../docs/design/adr/ADR-0053-write-side-aggregates-and-commands.md)), so you model the entity as an aggregate rather than reaching for a lock. A standalone `lock()` is only needed for **cross-aggregate / cross-resource** critical sections (the residual minor DX add).

**Net:** the two closest comparables surface **no major new gaps** — they primarily *validate* HoBo's architecture, with a couple of minor additive capabilities worth a future tranche if demand appears.

## 4. Review verdict
*(Superpowers `receiving-code-review` framing.)* **Strong-but-uneven** *(original verdict)*. HoBo's intersection bet (agnostic IfC + durable event-sourced runtime + agents/Forge, self-hostable) is genuinely uncontested — no competitor spans it. The risks were **depth, not breadth**: (a) the **unique** differentiator (Forge generation) was the least-specified; (b) HoBo lacked the one piece of mainstream DX a TS-backend audience expects (**reactive queries**); (c) several "designed" capabilities were blocked on unresolved open questions (wasm host, matching algorithm, data migration) that competitors had already shipped answers to. None fatal; all addressable in the design phase.

> **Update — depth gaps closed.** Every prioritized gap is now designed end-to-end via interactive brainstorm + ADR: reactive queries (**G1** → Plan 32/ADR-0029), Forge generation (**G3** → Plan 33/ADR-0030), wasm host-of-record (**Q10** → ADR-0031), app-data migration (**G5/Q15** → Plan 34/ADR-0032), Matching algorithm (**Q3/ADR-P4** → ADR-0033), search/vector (**G2/Q22** → Plan 35/ADR-0034), custom-domains/ingress (**G4/Q23** → ADR-0035), air-gap/sovereign (**G6** → ADR-0036), and SDK codegen (**G7** → ADR-0037). The "depth" critique is resolved; the intersection bet now has the specified substance to back it. Remaining work is the deferred operational/federation questions (#16/#18/#19/#20), not competitive gaps.
