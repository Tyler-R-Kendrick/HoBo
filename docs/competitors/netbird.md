# NetBird — Competitor Reference

> Captured for HoBo competitive analysis under the HoBo Competitive Research Contract.
> Research date **2026-08-20**. Read alongside [Tailscale](tailscale.md), which occupies the same
> position with a commercial coordination plane; the adapter-level integration detail lives in the
> [Tailscale technology reference](../technologies/tailscale.md).

## What it is

NetBird is "an open source platform consisting of a collection of components, responsible for
handling peer-to-peer connections, tunneling, authentication, and network management"
([how NetBird works](https://docs.netbird.io/about-netbird/how-netbird-works)). Functionally it
occupies the same ground as Tailscale; architecturally its distinguishing property is that **every
component is open source and self-hostable**, coordination plane included.

- **Product boundary.** Overlay connectivity and network access control. No workload hosting.
- **Operating model.** Open-source, self-hosted in full, with a commercial cloud offering.
- **The differentiator is sovereignty.** Tailscale's exit path depends on a third-party
  re-implementation of its coordination protocol; NetBird's coordination plane *is* the product's own
  code. For an air-gapped or jurisdiction-constrained deployment that is a categorical difference,
  not a preference.

## Core primitives and mental model

| Primitive | What it is |
| --------- | ---------- |
| **Management service** | Registers and authenticates peers, holds the network map, assigns addresses from `100.64.0.0/10`, distributes changes, and owns access-control rules and DNS |
| **Client** | Generates WireGuard keys — "the private key, generated by the NetBird client, never leaves the machine" — registers, and applies firewall policy locally |
| **Signal service** | Peer discovery and candidate exchange; "messages that are sent over Signal are point-to-point encrypted, so Signal can't see the contents" |
| **Relay service** | A TURN server (Coturn) for traffic that cannot go direct; still WireGuard-encrypted, so the relay "can't decrypt" it |
| **Peer** | A machine in the mesh |
| **Setup key** | The enrolment credential for unattended or machine registration |
| **Access-control policy** | Rules limiting which peers may reach which |
| **Posture check** | A device-condition input to access decisions |

The mental model is identical to Tailscale's — **reachability follows identity** — with the four
services made explicit and separately deployable, which is what makes the self-hosted story real.

## Feature surface

- Zero-configuration WireGuard mesh with NAT traversal and TURN relay fallback.
- SSO/IdP integration for user identity; setup keys for machine enrolment.
- Access-control policies between peer groups.
- Posture checks as an access input.
- Network routes to reach non-NetBird subnets, and DNS management.
- Activity/audit logging.
- Full self-hosting of management, signal and relay, plus a managed cloud option.
- Kubernetes operator and container deployment paths.

## Architecture

- **Four separable services.** Management (coordination and policy), Signal (discovery), Relay
  (TURN), and the client. That the roles are named and independently deployable is the architectural
  contribution: a customer can host all of it, or host only the sensitive parts.
- **Key custody.** Private keys are generated on the device and never leave it, so the coordination
  plane brokers public keys and never holds the means to decrypt.
- **Data plane** — WireGuard, peer to peer where possible, relayed where not, encrypted either way.
- **Address space** — the carrier-grade NAT range `100.64.0.0/10`, so overlay addresses do not
  collide with private networks.
- **State authority** — the management service, which the customer can own.
- **Portability boundary** — the protocol is WireGuard and the coordination plane is open source, so
  the exit is "keep running it". This is the strongest portability position of any networking product
  in the corpus.

## How it competes with HoBo

It does not compete; it is the adapter that makes a HoBo claim honest.

| Contested HoBo surface | The relationship |
| ---------------------- | ---------------- |
| `identity-secrets` | Identity-keyed reachability, self-hostable |
| `runtime-portability` | Cross-Yard connectivity for environments where a SaaS coordination plane is disqualifying |
| `governance` | Access policy and audit under the customer's own control |

Per ADR-0122, WireGuard is the portable floor and managed meshes are opt-in adapters. NetBird is the
adapter for **sovereign and air-gapped Yards (ADR-0036)**, where Tailscale's coordination plane is
not an option.

## Primitive mapping

| NetBird | Nearest HoBo concept | Honest correspondence |
| ------- | -------------------- | --------------------- |
| Management service | Junction overlay control | Close; NetBird's is self-hostable, which is the property HoBo needs. |
| Peer + setup key | Node attach with a recorded credential | **Close, and instructive.** A setup key is an unattended machine-enrolment credential — exactly the shape HoBo's node-attach path needs. |
| Access-control policy | `@hobo/policy` network rules | Close in role, network-scoped. |
| Signal / Relay separation | Fallback ladder in ADR-0143 | Close in spirit; NetBird names the roles, which HoBo's ladder would benefit from doing. |
| Key never leaves the machine | Least-privilege credential handling | **The idea worth taking.** The control plane brokers public keys and holds nothing that can decrypt traffic. |
| Posture check | Admission input | Partial; HoBo has no device-condition input to placement. |
| `100.64.0.0/10` addressing | — | Operational detail, but a good one: overlay addressing that cannot collide. |
| — | `evaluateResidency` | **No equivalent**, and the same jurisdiction caveat applies as for any overlay. |

## Where NetBird is stronger

- **Genuine self-hosting, coordination plane included.** This is the whole reason the capture exists,
  and it is the difference between "sovereign deployment supported" being true or being marketing.
- **The four-service decomposition is honest.** Management, Signal and Relay have distinct trust
  properties, and separating them lets a customer make different decisions about each.
- **Key custody is stated plainly** — the private key never leaves the machine, Signal cannot read
  messages, the relay cannot decrypt. Three specific claims rather than one reassurance.
- **Open source end to end**, so the exit cost is operational rather than architectural.
- **Setup keys** are a well-designed answer to unattended machine enrolment, which is the case that
  matters for infrastructure rather than laptops.
- **Kubernetes-native deployment paths**, which suit the environments where self-hosting is required.

## Where HoBo is stronger or intentionally different

State labels follow the research contract.

- **Different layer** (*implemented*). NetBird connects machines; HoBo describes and places
  applications.
- **Identity for authorization, not only reachability** (*implemented*).
- **Placement and residency as decisions** (*implemented*, `match.Decided`, ADR-0146). The overlay is
  deliberately indifferent to where things are.
- **Honest caveat.** NetBird is more mature than HoBo at everything NetBird does, and HoBo's
  sovereign-connectivity story depends on it rather than improving on it.

## Adversarial critique

- **Self-hosting is a commitment, not a checkbox.** Management, Signal and Relay are three services
  to run, secure, upgrade and keep highly available — and a coordination-plane outage stops new peers
  joining and policy propagating.
- **The relay is a bandwidth cost centre.** TURN traffic for peers that cannot connect directly runs
  through infrastructure someone pays for and sizes, and NAT topology decides how much.
- **Smaller ecosystem and maturity than the commercial incumbent.** Fewer platform integrations,
  fewer edge cases already found, a smaller operational corpus to learn from.
- **Open source with a commercial cloud** carries the familiar risk that the self-hosted path lags
  the hosted one; buyers should check which features are which rather than assuming parity.
- **The overlay hides geography.** Identical criticism to Tailscale, identical consequence for
  residency evaluation, and no better answered here.
- **Setup keys are long-lived credentials** unless scoped and rotated, and unattended enrolment is
  exactly where that discipline slips.
- **Posture checks depend on the client reporting honestly** about a machine that may be compromised,
  which bounds what they can be trusted to enforce.

## Better-together / integration posture

- **Adopt** — as the self-hosted managed-mesh adapter behind the `mesh` port, alongside Tailscale and
  Headscale, per ADR-0122 and ADR-0036.
- **Provider-target** — realizes overlay offerings in the ADR-0143 fallback ladder for sovereign
  Yards.
- **Borrow** — three things:
  1. **Name the roles in the connectivity ladder.** Management/Signal/Relay have different trust
     properties; HoBo's ladder currently treats fallback as a sequence rather than a set of distinct
     trust decisions.
  2. **Setup keys as the node-attach credential shape**, scoped and expiring, for HoBo's own
     node-attach path.
  3. **State the custody claims explicitly.** "The private key never leaves the machine" is a
     specific, checkable assertion; HoBo's security documentation should make claims of that shape
     rather than general assurances.
- Not a displace or benchmark target beyond connectivity ergonomics.

## Threats and lessons

1. **Sovereignty requires the coordination plane to be self-hostable.** Any HoBo claim about
   air-gapped or jurisdiction-constrained deployment is only as good as the least self-hostable
   component in the path. NetBird is what makes the connectivity leg of that claim true, and
   HoBo should name it rather than gesturing at "an overlay".
2. **Specific custody claims beat general assurances.** Three checkable statements about what each
   component cannot do is a better security story than a paragraph about encryption, and it is a
   documentation pattern HoBo should adopt directly.
3. **Unattended enrolment is its own problem.** Machines join without a human, and setup keys are the
   category's answer. HoBo's node-attach path needs an equivalent with scope and expiry designed in,
   not added later.
4. **An open coordination plane changes the portability argument.** With NetBird the exit from an
   overlay is operational; with a SaaS coordination plane it is architectural. That distinction is
   exactly the one HoBo makes about providers, arriving from the network layer.
