# Plan 8 — v1 delivery plan / build sequence

> Part of the [HoBo Design Plan Suite](./README.md). **HoBo ships as a single v1**: the entire designed surface — every plan in this suite — is v1 scope. There is no v2/v3/… release split and no "post-v1" bucket ([ADR-0063](./adr/ADR-0063-single-v1-scope.md), superseding [ADR-0022](./adr/ADR-0022-mvp-scope-moscow.md)). To deliver a large v1 quickly and effectively, the build is **dependency-ordered into stages** — you can't build multi-provider before the core, or Forge before conformance — but each stage is part of the *one* v1, not a separate version. Each stage names its acceptance gate ("done when…").

> **Stepwise breakdown:** each build stage below is fully expanded — every workstream and step — under [`phases/`](./phases/README.md) ([Stage 0](./phases/P0-foundations.md) · [Stage 1](./phases/P1-sdk-local.md) · [Stage 2](./phases/P2-first-deploy.md) · [Stage 3](./phases/P3-ai-native.md) · [Stage 4](./phases/P4-multi-provider.md) · [Stage 5](./phases/P5-forge.md) · [Stage 6](./phases/P6-ha-finops-ux.md)). These are build stages of v1, not release versions.

## v1 build stages (dependency order, all v1)
The themes below are *build sequence within v1*, not releases. v1 is done when **every** stage's acceptance gate is green.

| Stage | Theme | Key deliverables | Stage acceptance gate |
|---|---|---|---|
| **0** | Foundations | monorepo ([1](./01-monorepo.md)); `@hobo/core` types + all port interfaces; event envelope + catalog ([11](./11-event-model.md)); Capability Manifest schema ([6](./06-ai-native-agent-auth.md)); `@hobo/conformance` skeleton; `@hobo/runtime-local` built-in engine | local runtime passes runtime-port conformance; an event log replays |
| **1** | SDK on local runtime | `bindle()` + resources + `workflow`/`step`/`actor`/`saga`/`agent`; `hobo dev`; `examples/hello-bindle` | example runs offline; `replay == state` determinism test green ([2](./02-sdk-api.md),[9](./09-verification-open-questions.md)) |
| **2** | First real deploy | one provider (Cloudflare or Fly) via `@hobo/iac-pulumi`; `hobo plan`/`deploy`; Yard (single-node, `runtime-postgres`); event-sourced deployment lifecycle ([4](./04-control-plane.md)); contracts/`can-deploy` + policy plane gate the first deploy | a Bindle deploys to one real cloud and survives a Yard restart mid-deploy; an incompatible change is blocked with a precise reason |
| **3** | AI-native core | Identity (SVID/OIDC) + Registry + Capability Manifest ingest; keyless token brokering; `@hobo/mcp` surface; durable `agent()`; the Operator Crew core | an agent deploys via MCP using only brokered tokens; credential audit present ([6](./06-ai-native-agent-auth.md)) |
| **4** | Multi-provider | AWS + Azure providers; mapping rules (whole-app / per-tier / per-boundary) + provider-specific `.with(...)`; cross-provider networking ([13](./13-networking-connectivity.md)); `hobo import` onboarding | `examples/multi-cloud-shop`: one Bindle on two clouds; cross-cloud mTLS works; switching a resource's provider touches only config |
| **5** | Forge | AI-generated providers & implementations gated by `@hobo/conformance`; signing + provenance ([6](./06-ai-native-agent-auth.md),[12](./12-security-multitenancy.md)); eval-gated promotion | `hobo forge <url>` produces a certified provider that passes conformance |
| **6** | HA, FinOps, UX & governance planes | reliability/HA algorithms ([5](./05-reliability-ha.md)); deployment strategies; cost model + budgets + showback ([16](./16-cost-finops.md)); full dashboard ([7](./07-ui-dashboard.md)); multi-region/DR; SRE/incident management; the `notify` port · governance enforcement · AI-safety · Registry distribution | canary auto-rollback works; plan-time cost estimate within tolerance; DR rebuild from log < target RTO; dashboard renders every view from projections |

## Success metrics (north-star signals — v1 targets)
- **Time-to-first-deploy** (scaffold → running on a real cloud) — target minutes, not hours.
- **"Same Bindle, N clouds"** — number of providers a single unedited example deploys to.
- **Zero-secret rate** — % of provider access via brokered/federated tokens vs static keys (target ~100%).
- **Agent-completable lifecycle** — % of deploy/operate tasks an agent can do via MCP unaided.
- **Forge yield** — % of requested providers auto-generated that pass conformance.
- **Recovery** — deploy resume time after node loss; projection-rebuild time.

## Sequencing rationale
One v1, built in dependency order. Stages 0–2 stand up the *agnostic deploy* core on one cloud (with governance gating it from the first deploy); stage 3 makes it *AI-native*; stage 4 proves *true multi-provider*; stage 5 adds *extensibility without a community* (Forge); stage 6 hardens for production and lands the breadth (HA, FinOps, full UX, SRE, the `notify` port + governance enforcement + AI-safety + Registry distribution). The risky/novel bets (Forge, multi-region HA) build on a demonstrably solid core, but all of it is v1 — the stages are *how* we deliver a large v1 quickly, not a schedule of separate releases.
