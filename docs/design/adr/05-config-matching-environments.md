# Config, matching, environments, codegen & DSL — consolidated decisions

> Consolidated ADR decisions for **config, matching, environments, codegen & dsl**. Each section is one architecture decision; see [`README.md`](./README.md) for the full ADR index.

## ADR-0033
**Deterministic Matching & Planner selection (+ default objective).**

- **Origin:** the gap analysis asked, of HoBo's Humanitec-parity Matching, *"which algorithm — rules, constraint solver, or LLM — and is it deterministic enough to trust in prod?"* ([Q3](../verification.md#plan-09)). Designed via brainstorming + grill-with-docs.

### Context
[Plan 25](../platform-engineering.md#plan-25) introduced **Resource Definitions** + **specificity-scored Matching** and the auditable **`match.Decided`** event; [Plan 4](../control-plane.md#plan-04) made the **Planner a pure function** with capability negotiation (`require` hard / `prefer` soft), region/colocation, and an *optional* cost-shaping step. But three things were left open and they are what make Matching trustworthy in prod: (1) the **algorithm class** — pure rules vs a constraint solver vs LLM-assisted, and whether selection is **deterministic/replayable**; (2) the **default objective** when several candidates fully satisfy (Plan 3 §122's objective hook; the open **ADR-P4**); (3) **tie behaviour** when definitions are equally specific. Humanitec's selection is specificity-based but **opaque**; HoBo's differentiator is an auditable, replayable decision — which only holds if selection is deterministic.

### Decision
1. **Selection on the deploy path is deterministic rules — a pure function.** Selection is a pure function of `(catalog snapshot, deploy context, objective setting)` — **no clock, RNG, network, or model** — so it is unit-testable without a cloud and **identical on replay** (the property [Plan 9](../verification.md#plan-09) already asserts of the Planner). **AI and cost/constraint *solvers* are advisory only, off the deploy path:** `hobo plan` may *surface* a cheaper alternative; the **Forge** may *generate* candidate definitions ([Plan 23](../forge-generated-stack.md#plan-23)); an LLM may *suggest* definitions at authoring time. None select at deploy time, so replay + `match.Decided` stay honest.
2. **The pipeline is gather → filter → rank → record:**
   - **Filter** to candidates whose criteria match the context **and** whose provider satisfies the resource's hard **`require`** capabilities (`Capability.satisfies` = `full` → accept; `prefer` may degrade with a `PlanWarning`; `require` miss → reject). If none satisfy `require` → **`deployment.PlanRejected`** with a precise, agent-correctable reason.
   - **Rank lexicographically:** (a) **specificity score** ([Plan 25](../platform-engineering.md#plan-25)) → (b) **explicit platform priority** (a new optional `priority` field on a definition, for deliberate override) → (c) the **default objective** (soft) → (d) a **stable deterministic tiebreak** (definition id, lexicographic).
3. **The default objective is configurable, defaulting to min-cost within constraints** (resolves **ADR-P4**). The objective is a Yard/Camp setting — `cost` | `latency` | `single-provider` | `carbon` | **`maximize-credits`** (credit/budget-aware cost, [ADR-0071](#adr-0071)) — defaulting to **lowest cost subject to satisfying `require`/`prefer`/region/colocation**. The region/colocation step ([Plan 4](../control-plane.md#plan-04) §4) already minimizes cross-provider egress, so cost is the natural remaining optimizer; the chosen objective is recorded in `match.Decided`/`deployment.Planned`.
4. **A true tie gets a stable tiebreak + a warning, never a block.** When candidates are equal on specificity, priority, and objective, break by the stable key (definition id) so the result is always deterministic + replay-stable, **and** emit a `PlanWarning` + flag the tie in `match.Decided` so a platform engineer can add an explicit `priority` to disambiguate.
5. **Enrich `match.Decided`; add no new event types.** Its payload carries the winner, the full ranking, the rejected candidates (with reasons), the objective used, and the tie flag.
6. **Static provider-capability feedback with remediation, at author time.** Registered providers/deps **advertise the capabilities they support** (the same `Capability` model the filter uses, sourced from the Capability Manifest, [ADR-0009](02-identity-security.md#adr-0009)). The SDK + Matching evaluate this **statically (compile-time)**: when a configuration uses a capability the selected provider does **not** support, surface **compile-time feedback** at the authoring site — and **suggest a remediation** (e.g. "provider X doesn't support containers — host them on registered provider Y that does"). This is **in addition to** the deploy-time `can-deploy`/`require`-miss rejection in (2): the same capability check runs early, against the catalog snapshot, so unsupported configurations are caught at author time with an actionable suggestion rather than only failing at deploy. Static feedback flows through the codegen surface ([ADR-0037](#adr-0037)) and `hobo doctor`; it is advisory at author time and remains backed by the hard `PlanRejected` gate on the deploy path.

### Alternatives considered
- **Constraint solver (e.g. ILP) on the deploy path.** Rejected: solver outputs can be unstable across versions, are harder to explain in `match.Decided`, and risk non-determinism on replay unless heavily pinned — overkill for the indie/agent ICP. (Cost optimization survives as the *soft objective* and as an *advisory* `hobo plan` suggestion.)
- **LLM-assisted selection on the deploy path.** Rejected: non-deterministic → breaks replay and makes `match.Decided` unauditable; unacceptable for prod infra selection. Retained only as an authoring-time *suggester*.
- **Error out on a true tie (require disambiguation).** Rejected as the default: blocks deploys/iteration on an ambiguous catalog (bad for agents + ephemeral previews); the stable-tiebreak-plus-warning keeps deploys moving while surfacing the ambiguity. (A Yard may still opt into strict mode via policy, [Plan 29](../contracts-policy-flags.md#plan-29).)
- **Most-recently-updated wins.** Rejected: not replay-stable (timestamp isn't a clean deploy input) and changes silently as the catalog is edited.
- **A fixed, non-configurable objective.** Rejected: teams legitimately want latency- or single-cloud-first; configurability with a sane default serves both.

### Consequences
- **(+)** Matching becomes **demonstrably deterministic + auditable** — "why did this resource land on this infra?" is answerable and reproducible, closing the credibility gap vs Humanitec's opaque selection.
- **(+)** Reuses the **pure Planner** ([Plan 4](../control-plane.md#plan-04)), specificity scoring + `match.Decided` ([Plan 25](../platform-engineering.md#plan-25)/[Plan 11](../event-model.md#plan-11)), and cost signals ([Plan 5](../reliability-observability-cost.md#plan-05)); little new machinery (an optional `priority` field + an enriched event payload).
- **(+)** AI keeps adding value (Forge-generated + LLM-suggested definitions) **without** compromising determinism, because it sits off the deploy path.
- **(+)** Capability mismatches are caught at **author time** with a concrete remediation, not just rejected at deploy — a faster, more actionable loop for humans and agents, reusing the same advertised-capability model as the deploy-path filter.
- **(−)** Pure rules can pick a sub-optimal option a full solver might improve on; mitigated by the soft cost objective + the advisory `hobo plan` suggestion + explicit `priority`.
- **(−)** Platform engineers must occasionally add a `priority` to silence a tie warning — a small, explicit authoring cost in exchange for predictability.

## ADR-0071
**The Dispatcher: credit/budget-aware cost routing across registered providers (placement · dispatch · traffic).**

- **Origin:** with multi-provider support ([ADR-0026](01-architecture-core.md#adr-0026)/[ADR-0043](07-portability-extensibility.md#adr-0043)) the same workload can run on several registered providers at very different effective cost — and free tiers / promotional credits / committed budgets make "cheapest" *time-* and *usage-varying*, not a static price. The ask: make cost-based routing a **native capability that leverages every registered provider** (and only those) to maximize free credits/budgets — for app services, **CI action runners**, and **build machines** alike. Designed via brainstorming.

### Context
HoBo already has **one deterministic selector** — Matching/Planner ([ADR-0033](#adr-0033)): it ranks candidate providers by a configurable objective (default min-cost), considers **only registered Resource Definitions/providers**, and records the choice as `match.Decided` (replayable "why this infra"). Cost is already the soft objective ([Plan 5](../reliability-observability-cost.md#plan-05)) and app-traffic routing is already event-sourced ([ADR-0035](07-portability-extensibility.md#adr-0035)). Three things are missing: (1) a notion of **effective marginal cost** that accounts for free-tier headroom / promotional credits / budget caps that *deplete and reset over time* — without it "min-cost" can't express *"burn the free GitHub Actions minutes first, then rotate to Blacksmith"*; (2) the same selector applied to **CI/action-runner** and **build-machine** execution, which today run on the Executors with no provider choice; (3) one named home for "cost routing" so it is a deliberate capability, not scattered tiebreaks. The hard constraint is ADR-0033's: selection on the path stays **deterministic + replayable** — no live solver, no model, on the deploy/dispatch path.

### Decision
1. **The Dispatcher is the credit/budget-aware generalization of the deterministic selector — one mechanism, three decision points.** It is the same gather → filter (hard `require`) → rank → record pipeline as [ADR-0033](#adr-0033), applied at: **placement** (which registered provider hosts a resource — the existing Matching path, `match.Decided`), **dispatch** (which registered runner / build-machine executes *this* CI job or *this* build, `dispatch.Decided`), and **traffic** (for a service live across ≥2 Camps/providers, which backend serves work, `domain.RoutingChanged`). It considers **exactly the providers the developer/platform registered** — every one is a candidate, none outside the set — inheriting Matching's candidate-gathering, so it is non-limiting by construction.
2. **Effective marginal cost is the ranking signal, derived from a `CreditLedgerView` projection.** A `CreditLedgerView` folds, per registered provider, its **free-tier allotments + reset windows**, **promotional/committed credits + expiry**, **budget caps**, and **spend-to-date** off the existing log (`meter.*`/`spend.*`, [ADR-0039](04-governance-verification.md#adr-0039)) plus a few declared facts (`credit.Registered`/`credit.Reset`/`credit.Exhausted`, [Plan 11](../event-model.md#plan-11)). From it the Dispatcher computes the **effective marginal cost of the next unit of work** — `0` while free headroom/credit remains (optionally preferring *expiring* credit first), list price (`cost.json`, [Plan 5](../reliability-observability-cost.md#plan-05)) after. A new objective mode **`maximize-credits`** ranks by this; `min-cost`/`latency`/`single-provider`/`carbon` are unchanged. *"Maximize free credits/budgets"* then falls out with **zero hardcoded provider logic**: the ranker prefers whoever has free headroom now and **rotates as each is exhausted or resets**.
3. **Determinism is preserved by recording the ledger into the decision context.** The ledger is read at a `seq` and **recorded into the decision** (alongside the catalog snapshot + context + objective), so placement/dispatch remain a **pure function of recorded inputs** and replay identically — no on-path solver/model ([ADR-0033](#adr-0033) intact). The AI/advisory layer (the Platform Engineer operator suggesting *"register Depot to save,"* `hobo plan` surfacing a cheaper mix) stays **off-path**, exactly as ADR-0033 mandates. Live **traffic** routing (ops, like DNS failover) is not per-request deterministic but each decision is event-sourced ([ADR-0035](07-portability-extensibility.md#adr-0035)).
4. **CI action runners and build machines are first-class cost-routable provider categories.** A **`runner`** category (`hobo:runner`; adapters: self-hosted · GitHub Actions · Blacksmith · Depot) executes CI/action jobs; **`build-machine`** deepens the existing `BuildProvider` ([ADR-0005](01-architecture-core.md#adr-0005); adapters: self-hosted · GitHub · Blacksmith · Depot) into the host a build *runs on*. Pipelines ([Plan 25](../platform-engineering.md#plan-25)) ask the Dispatcher per job/build; the chosen provider is recorded in `dispatch.Decided`. Both plug into the **same** selector + ledger as any other provider — registering one makes it a candidate; that is the whole integration.
5. **Cost routing is a policy, configured per Yard/Camp, composing with the existing FinOps planes.** Objective + hard constraints (stay-in-budget, residency, capability `require`) + the candidate set are a policy-plane configuration ([Plan 29](../contracts-policy-flags.md#plan-29)); it composes with the spend circuit-breaker + `costAvailabilityProfile` ([ADR-0039](04-governance-verification.md#adr-0039)) and obeys data-residency obligations ([ADR-0060](04-governance-verification.md#adr-0060)). The Dispatcher operates at the **Yard** for provider-internal cross-Camp routing and at the **Junction** for cross-cloud ([ADR-0026](01-architecture-core.md#adr-0026)/[ADR-0043](07-portability-extensibility.md#adr-0043)).
6. **Honest limits.** Live **traffic** routing applies only to **stateless / replicable** workloads — stateful traffic can't be freely re-routed without data gravity/egress, which the Dispatcher *accounts for* (egress is a cost term, [Plan 5](../reliability-observability-cost.md#plan-05)) but cannot wish away; cross-provider data moves obey the migration equivalence classes ([ADR-0032](03-data-plane.md#adr-0032)). Switching has churn cost (cold start, cache loss), so the Dispatcher applies **dwell-time / hysteresis** and won't thrash. Free-credit accounting is **best-effort** against provider-reported usage (reconciled like all cost estimates, [Plan 5](../reliability-observability-cost.md#plan-05)).

### Alternatives considered
- **A live cost/credit solver (or LLM) on the dispatch path.** Rejected: breaks replay + makes `dispatch.Decided`/`match.Decided` unauditable — the exact rejection [ADR-0033](#adr-0033) already made. Optimization survives as the recorded `maximize-credits` ranking + off-path advisory.
- **A standalone "cost router" subsystem.** Rejected: it would duplicate gather/filter/rank/record; the Dispatcher is deliberately the *same* selector at more decision points, so determinism, `require`-gating, and the audit event are reused, not reinvented.
- **Hardcoded provider-rotation rules** (*"use GitHub until 2000 min, then Blacksmith"*). Rejected: not extensible (every new provider edits the rule) and not portable; the ledger-derived effective marginal cost makes rotation **emergent** from registered providers + their declared free tiers.
- **An AI Operator (the Crew) owning the routing decision.** Rejected for the *decision* (must be deterministic/on-path); the Crew's Platform Engineer ([Plan 40](../operators-sre.md#plan-40)) stays the off-path *advisor* (suggest registering a provider, propose a cheaper mix as a gated Delta).
- **Per-request routing of stateful traffic.** Rejected: data gravity/egress make it incorrect or expensive; traffic routing is scoped to stateless/replicable, with placement + scheduled rebalancing covering the rest.

### Consequences
- **(+)** Cost optimization becomes a **native, auditable capability** spanning app services, CI runners, and build machines — *"maximize free credits/budgets across every cloud I registered"* is a single objective setting, not bespoke glue.
- **(+)** Reuses the deterministic selector ([ADR-0033](#adr-0033)), the metering projection + circuit-breaker ([ADR-0039](04-governance-verification.md#adr-0039)), cost signals + egress model ([Plan 5](../reliability-observability-cost.md#plan-05)), and event-sourced routing ([ADR-0035](07-portability-extensibility.md#adr-0035)) — net-new is a ledger projection, three `credit.*` facts + `dispatch.Decided`, two provider categories, and the `maximize-credits` objective.
- **(+)** Strictly **non-limiting**: the candidate set is exactly the registered providers; adding one (self-hosted/GitHub/Blacksmith/Depot/any cloud) makes it eligible with no app-code change, and the Forge can generate a missing runner/build-machine adapter ([Plan 23](../forge-generated-stack.md#plan-23)).
- **(−)** Effective-marginal-cost quality depends on providers declaring free tiers/credits + on usage reconciliation; a mis-declared free tier mis-ranks (mitigated: estimates are reconciled against real usage and recorded as a delta, [Plan 5](../reliability-observability-cost.md#plan-05)).
- **(−)** Adds a credit-ledger surface platform engineers populate (free-tier/budget facts) to get the benefit; absent any credit facts, the Dispatcher degrades to plain min-cost ([ADR-0033](#adr-0033)).
- **(−)** Cross-provider dispatch of builds/CI can incur artifact/cache egress between runs; the Dispatcher accounts for it, but a naive free-tier chase can cost more in egress than it saves — bounded by dwell-time + the egress cost term.

## ADR-0028
**Multi-Camp deployment model (cardinality, naming, atomicity).**

- **Origin:** design review of ADR-0026 surfaced unresolved cardinality/atomicity/naming questions ([`plans/0001-scope-refactor-review.md`](../../../plans/0001-scope-refactor-review.md)).

### Context
ADR-0026 made a **Camp** provider-specific and nested `Yard ⊃ Camp ⊃ Bindle`, but left three things ambiguous that a review flagged HIGH:
1. **Cardinality:** does one Bindle deploy to one Camp or many? The worked example ([19](../worked-example.md#plan-19)) splits one app's resources across clouds.
2. **Naming:** Camps keyed by environment (`prod`, `staging`) vs a Camp being "provider-specific" — so is `prod` or `prod-aws` the Camp?
3. **Atomicity:** Deployment Sets/Deltas/promote ([26](../platform-engineering.md#plan-25)) are per-Camp; a multi-cloud `production` has no atomic promote/rollback unit.

### Decision
1. **A Camp is provider-specific; its canonical id is `<env>-<provider>`** (e.g. `prod-aws`, `prod-azure`, `staging-gcp`). A Camp carries an `environment type` ([25](../platform-engineering.md#plan-25)) and provides one provider's infra + one runtime backend.
2. **A Bindle deploys to one *or more* Camps.** Single-cloud = one Camp. Multi-cloud / hybrid = the **same Bindle deployed across several Camps** under one Yard. Resource→Camp placement is expressed in the Camp's mapping (per-resource/per-tier on the `camp()` object), not in app code — preserving "no app edits to change where things run".
3. **Cross-Camp `bind` edges are wired by the enclosing scope.** A `bind` between Camps under the **same provider** (e.g. two Azure Camps in different regions) is provisioned by the **Yard** (cross-Camp connectivity tier, [13](../security-networking.md#plan-12), mTLS by SVID). A `bind` that crosses **providers** (e.g. `api`@`prod-aws` → `db`@`prod-azure`) is federated by the **Junction** ([ADR-0043](07-portability-extensibility.md#adr-0043)). The data plane still talks directly (neither is on the request path).
4. **An "environment group" is the multi-cloud atomic unit (a Yard-level saga, not a new config layer).** A logical environment (e.g. `production` = {`prod-aws`, `prod-azure`}) groups its member Camps by `environment type`. `hobo deploy/promote/rollback --env production` runs a **choreographed saga** ([05](../reliability-observability-cost.md#plan-05)) over the member Camps' per-Camp Sets/Deltas, emitting `env.PromoteRequested → (per-Camp promote) → env.Promoted | env.PromoteRolledBack`; a member failure compensates the group (or proceeds if the member is marked `optional`). `--camp prod-aws` still targets a single Camp. The group is **orchestration over Camps, not a 4th scope noun**.

### Alternatives considered
- **One Bindle → exactly one Camp; multi-cloud handled entirely by the Planner inside a single "multi-provider Camp."** Rejected: makes a Camp not-actually-provider-specific (contradicts ADR-0026) and hides cross-provider cost/topology from the model.
- **Add a 4th config layer "Environment" (`Yard ⊃ Env ⊃ Camp ⊃ Bindle`).** Rejected: ADR-0026 deliberately kept environment a matching dimension; the group is a thin saga, not a persistent scope.
- **Name Camps by environment only (`prod`) and infer providers.** Rejected: hides the provider, breaks "provider-specific", and makes two `prod` Camps on different clouds indistinguishable.

### Consequences
- **(+)** Resolves cardinality (Bindle→1..N Camps), naming (`<env>-<provider>`), and atomicity (env-group saga reusing existing compensation). The worked example is now precise: splitting providers = deploying the Bindle to multiple Camps the Yard wires together.
- **(+)** Per-Camp Sets/Deltas/`can-deploy` are unchanged; the group composes them.
- **(−)** Requires `env.*` group-saga events + a group view in the dashboard, and a clear story for partial-success across clouds (covered by saga compensation + `optional` Camps).
- **(−)** Cross-Camp app boundaries inherit cross-provider latency/egress; the Planner still prefers colocation ([13](../security-networking.md#plan-12)/[16](../reliability-observability-cost.md#plan-05)) and `hobo doctor` warns on accidental cross-cloud edges.
- **Related decisions:** stateful-data consistency across Camps is owned by [ADR-0040](#adr-0040) (declared replication topology, single-writer-Camp default, event-log backbone, labeled bounded-staleness + write-goes-home); app-data migration is owned by [ADR-0032](03-data-plane.md#adr-0032) ([Plan 32](../data-plane.md#plan-32)).

## ADR-0040
**Cross-Camp stateful consistency.**

- **Origin:** open question #16, the cross-Camp case [ADR-0028](#adr-0028) and the Plan 32 / Plan 34 / [ADR-0035](07-portability-extensibility.md#adr-0035) dependency depend on. Designed via brainstorming + grill-with-docs.

### Context
[ADR-0028](#adr-0028) makes a Bindle deployable to **1..N Camps** (multi-cloud), with cross-Camp `bind` edges Yard-wired and the data plane talking directly. The question: when a Bindle spans clouds, is cross-Camp state a HoBo *guarantee* (cross-cloud event replication) or an *app responsibility* (eventual)? It can't be silently strong — cross-provider quorum writes are high-latency and partition-prone (CAP). And it's load-bearing: Plan 32's cross-Camp reactive queries, Plan 34's cross-engine/CDC moves, and [ADR-0035](07-portability-extensibility.md#adr-0035)'s cross-Camp traffic routing all build on it.

### Decision
1. **Cross-Camp state declares a replication topology; HoBo wires it and surfaces the guarantee — no silent strong consistency.** Per piece of cross-Camp state, the topology is one of: **single-writer-Camp** (one Camp owns the data; other Camps read — the **default**), **active-active-eventual** (CRDT / event-merge, opt-in), or **pinned-single-Camp** (data lives in one Camp; compute may still span). The topology is part of the resource's resolved config / Resource Definition ([Plan 25](../platform-engineering.md#plan-25)/[Plan 25](../platform-engineering.md#plan-25)), not app code.
2. **The event log is the cross-Camp replication backbone.** HoBo-native event-sourced state (actors, runs, projections) replicates **via the log**: the owning Camp is the single writer; other Camps consume a **replicated read-stream** into **bounded-staleness projections** (reusing event-store replication, [Plan 11](../event-model.md#plan-11), and the quorum/HA machinery, [Plan 5](../reliability-observability-cost.md#plan-05)). **Provider-backed stores** (`sql`/`kv`/`bucket`) default to **single-writer-Camp + cross-Camp read** over the connectivity tiers ([Plan 12](../security-networking.md#plan-12)); **active-active CDC / multi-primary for provider stores is the opt-in `active-active-eventual` topology** — the same per-engine CDC boundary [Plan 32](../data-plane.md#plan-32) draws for cross-engine moves.
3. **Consistency is surfaced honestly.** Reads from a non-owner Camp are **labeled bounded-staleness** (stale-by ≤ replication lag, reusing [Plan 5](../reliability-observability-cost.md#plan-05) §Control-plane-HA's labeled reads) — never silently stale. **Reads-your-writes** holds within the writer Camp (and cross-Camp after replication, observable via the stream `seq`/version). **Consistency-requiring writes "go home"** — they route to the owning Camp. **Cross-Camp reactive queries** ([Plan 32](../data-plane.md#plan-32)) subscribe to the owner Camp's reactor or a replicated-stream reactor that carries the staleness label.
4. **No new event types** — replication rides the existing event-store replication ([Plan 11](../event-model.md#plan-11)/[Plan 5](../reliability-observability-cost.md#plan-05)); a topology is resource config; staleness is a read-label + an observability signal ([Plan 5](../reliability-observability-cost.md#plan-05)) that can trip a policy obligation ([Plan 29](../contracts-policy-flags.md#plan-29)) when lag exceeds a bound.

### Alternatives considered
- **HoBo guarantees strong cross-cloud consistency (quorum event replication across clouds).** Rejected: high-latency + partition-prone across providers; makes a multi-cloud Bindle slow by default and over-promises against CAP. (Strong consistency *within* a Camp is unchanged — that's the runtime backend's quorum.)
- **Purely app-owned (HoBo only wires connectivity).** Rejected: abandons the multi-cloud-data promise and gives developers no patterns — the gap #16 exists to close.
- **Provider-native multi-region storage replication.** Rejected as the mechanism: provider-specific (breaks agnostic) and doesn't span *different* providers (the actual cross-Camp case). It can still realize a single-Camp's HA underneath.
- **A HoBo-managed global state store.** Rejected: puts HoBo on the data-plane request path (latency/cost/SPOF), contradicting [ADR-0028](#adr-0028) ("the Yard is never on the request path").
- **Active-active CDC for provider stores as the default.** Rejected as the default: heavy per-engine CDC + conflict handling, so it is the deliberate, opt-in `active-active-eventual` topology rather than the silent baseline ([Plan 32](../data-plane.md#plan-32)).

### Consequences
- **(+)** Resolves the keystone #16 and the cross-Camp cases in [Plan 32](../data-plane.md#plan-32) (reactive), [Plan 32](../data-plane.md#plan-32) (data move), and [ADR-0035](07-portability-extensibility.md#adr-0035) (ingress) — multi-cloud has an honest *data* story.
- **(+)** Reuses event-sourcing as the replication backbone, the Plan 5 quorum + labeled-staleness machinery, and the connectivity tiers — minimal new mechanism (a declared topology + a read label + a write-goes-home rule).
- **(+)** CAP-honest: developers see the real guarantee (bounded staleness, single-writer) and choose active-active-eventual deliberately where they can tolerate merge semantics.
- **(−)** Single-writer-Camp means the owning Camp is a write bottleneck/availability dependency for that state (mitigated by the owner Camp's own intra-Camp HA, [Plan 5](../reliability-observability-cost.md#plan-05)).
- **(−)** Active-active-eventual requires CRDT/merge modeling by the developer; HoBo provides the plumbing + event-merge, not automatic conflict resolution for arbitrary data.
- **(−)** Provider-store active-active/CDC is opt-in and per-engine, so cross-cloud data patterns are single-writer by default unless a topology is declared.

## ADR-0037
**SDK codegen surface & policy.**

- **Origin:** the gap analysis (G7) found HoBo *promises* "type-safe end-to-end" + WIT-generated clients but never *shows* the codegen DX, while Aspire/Convex make typed codegen a headline. Designed via brainstorming + grill-with-docs.

### Context
HoBo's typed surface is referenced throughout — `ctx.bindings.db` is "a provider-agnostic typed client" ([Plan 2](../sdk-api.md#plan-02)), "typed clients are generated from those interfaces (jco guest-types)" ([Plan 20](../wasm-runtime-wit.md#plan-20)), "type-safe end to end" ([Plan 7](../developer-experience.md#plan-07)) — but *what* is generated, *where* it lives, *when* it runs, and the developer-facing artifact were never specified. A Convex/Aspire audience expects a concrete codegen story (Convex commits `convex/_generated/`).

### Decision
1. **Sources → generated artifacts.** Codegen is a **deterministic pure function** of: the **WIT interfaces** (jco guest-types, [Plan 20](../wasm-runtime-wit.md#plan-20)) + **Zod schemas** (step/workflow/`query`/search I/O) + **`.allow()`** scopes ([Plan 21](../authoring-resources-wiring.md#plan-21)) + the **bindle graph** (`bind` edges, [Plan 21](../authoring-resources-wiring.md#plan-21)). It emits: typed `ctx.bindings.<name>` clients, typed `useQuery()`/search results ([Plan 32](../data-plane.md#plan-32)/[Plan 32](../data-plane.md#plan-32)), typed workflow/step signatures, typed provider `.with()` options, and a typed **`api` function-tree** reference.
2. **Location & commit policy: a checked-in `_generated/` directory** (`.hobo/generated/` or `src/_generated/`). Rationale: reviewable in diffs, gives editors types with **no build step**, and is **offline/air-gap-friendly** ([ADR-0036](07-portability-extensibility.md#adr-0036)). **`hobo codegen --check`** is a CI gate that regenerates and fails on drift.
3. **When it runs:** `hobo dev` regenerates on change (watch); `hobo build` regenerates + fails on drift; `hobo new` scaffolds an initial `_generated/`. Because generation is deterministic, the same sources always produce the same output (reproducible; replay/air-gap friendly).
4. **Agent parity:** an MCP `codegen` tool so agents regenerate + typecheck like the CLI ([Plan 6](../ai-native-agent-auth.md#plan-06)/[Plan 7](../developer-experience.md#plan-07)).
5. **Domain-schema emitters (WIT-record canonical, [ADR-0051](03-data-plane.md#adr-0051)).** When domain types are authored as WIT records ([Plan 32](../data-plane.md#plan-32)), codegen adds two deterministic outputs alongside the TS types: **protobuf** message descriptors (the event-body wire encoding, [Plan 11](../event-model.md#plan-11)) and **Zod** validators (a runtime-validation view of the record). Same `_generated/` location + `--check` drift gate; protobuf is an encoding, not an authoring source.

### Alternatives considered
- **Virtual / build-resolved types (nothing committed).** Rejected as the default: needs the toolchain running to get types, diffs don't show the generated surface, and the offline/air-gap + editor-without-build story is weaker.
- **Both (committed default + virtual mode).** Rejected to avoid two codegen modes to document/test/keep consistent; the checked-in dir covers the cases that matter.
- **No dedicated codegen story (leave it implied).** Rejected: the gap analysis (G7) is exactly that this was unstated; a Convex/Aspire audience expects it shown.

### Consequences
- **(+)** Closes G7 with a concrete, reviewable, offline-friendly codegen DX that matches the Convex/Aspire expectation; editors get full types with no build step.
- **(+)** Reuses existing sources (WIT/jco, Zod, `.allow()`, the graph) — codegen adds an emitter + a CLI/MCP command + a CI check, not a new model; determinism fits the replay/air-gap ethos ([ADR-0036](07-portability-extensibility.md#adr-0036)).
- **(−)** A checked-in `_generated/` dir adds diff noise on schema/binding changes and a `codegen --check` CI step (the standard tradeoff for committed generated code).
- **(−)** Generated TS quality depends on the WIT→TS (jco) mapping fidelity; advanced WIT types may need hand-tuned emit.

## ADR-0049
**"Hobo Code" is the configuration + code DSL: a two-level authoring model.** Accepted; the DSL is in scope and fleshed out below.

- **Origin:** HoBo needs an AI-native authoring surface that configures **Yards/Camps/Bindles** *and* code in one human-readable form. "Hobo Code" names that DSL; the machine-readable **auth + capability standard** carries the accurate name **Capability Manifest**.

### Context
HoBo is **AI-native** — agents and the Forge generate, repair, and optimize HoBo artifacts ([Plan 6](../ai-native-agent-auth.md#plan-06)/[Plan 23](../forge-generated-stack.md#plan-23)/[Plan 23](../forge-generated-stack.md#plan-23)). The TypeScript+IfC surface ([Plan 2](../sdk-api.md#plan-02)/[Plan 21](../authoring-resources-wiring.md#plan-21)) is ideal for humans with an editor and a type-checker but a noisy generation/training target: large grammar, host imports, collection-time side-effects, hard-to-score ASTs. Hobo Code is a purpose-built DSL **optimal for AI generation, training, and optimization** — small, regular, declarative-first, deterministic, token-efficient, with a stable canonical AST. The open question this ADR settles is *how authors reach it*: directly, by writing code, or without writing code at all.

### Decision
1. **The Capability Manifest carries the auth+capability standard** ([Plan 6](../ai-native-agent-auth.md#plan-06)) — `index/signs/capabilities/auth/cost.json`, served at `/.well-known/capability-manifest/`, WIT `hobo:capability-manifest`. It is the machine-readable auth advertisement, distinct from Hobo Code (which is "code").
2. **Hobo Code is a two-level authoring model.** Authors enter at whichever level fits, and both compile to the same artifacts:
   - **Level 1 — declarative DSL/config (no code).** A first-class entry point: write the small, regular declarative surface ([Plan 21](../authoring-resources-wiring.md#plan-21)) to declare scope/topology (`Yard`/`Camp`/`Bindle` + resources + `.allow()` + `bind` wiring) and behavior shape (`workflow`/`step`/`actor`/`saga`/`agent`, trainable methods) **without writing code**. The same declarative path drives **initialization, specification, and code-generation** — an author (or the Forge) declares intent and gets a working stack.
   - **Level 2 — generated SDK code stubs (intermediary artifacts).** The DSL **generates SDK code-stub definitions** the developer drops into: typed `service`/`workflow`/`step`/`actor` skeletons, resource handles with `.allow()` pre-wired, and the `bind` graph stitched. Stubs are the seam where hand-written code lands; the author fills bodies, the declarative source stays the source of truth for topology.
3. **The flow is declarative DSL/config → generated SDK stubs → code.** The no-code declarative path is the front door; it emits SDK stubs (Level 2), and developers extend the stubs with behavior. A pure no-code stack is valid end-to-end (declarations alone produce a deployable Bindle); a code-heavy stack starts from the same declarations and grows.
4. **Hobo Code composes with Matching and codegen, adding nothing semantically new.** It is a **sibling authoring front-end** to the TypeScript SDK ([Plan 2](../sdk-api.md#plan-02)) — both are front-ends over the canonical **`hobo:sdk` WIT contract** ([ADR-0072](01-architecture-core.md#adr-0072)), alongside every language's idiom layer: all lower to the same **Manifest IR** ([Plan 21](../authoring-resources-wiring.md#plan-21)) and runtime constructs; the scope model is unchanged ([ADR-0026](01-architecture-core.md#adr-0026)). The generated SDK stubs are produced by **codegen** ([ADR-0037](#adr-0037)) — the same deterministic, checked-in `_generated/` discipline and `--check` drift gate — so DSL → stub output is reviewable and reproducible. Provider placement of declared resources runs through **deterministic Matching** ([ADR-0033](#adr-0033)); the DSL declares the resource graph, Matching resolves it to Camps. TS↔Hobo Code is mechanically convertible (both are views over the IR/AST), so teams mix surfaces and the Forge emits either.

### Alternatives considered
- **Keep "Hobo Code" for the manifest; pick another DSL name.** Rejected: the manifest is a *capability/auth advertisement*, not "code"; "Capability Manifest" describes it accurately, and "Hobo Code" is the natural name for an authoring language.
- **No DSL — TypeScript+IfC is the only surface.** Rejected: a general-purpose language is a poor AI generation/training/optimization target, and it forces every author through code even when a declaration would do.
- **DSL generates final code directly (no stub layer).** Rejected: the generated-stub seam is what lets developers drop in hand-written behavior while keeping the declarative source authoritative for topology; collapsing it loses the no-code↔code escape hatch.
- **Two levels, no shared IR (independent compilers).** Rejected: divergent semantics; both levels must lower to the one Manifest IR so Matching, codegen, and conformance ([Plan 9](../verification.md#plan-09)) apply uniformly.
- **A new runtime/semantics for the DSL.** Rejected: it is a pure front-end over the existing IR to avoid forking the model and to stay round-trippable with TypeScript.

### Consequences
- **(+)** One DSL serves both a **no-code declarative path** (init/spec/codegen without writing code) and a **code path** (generated SDK stubs the developer extends) — the widest authoring funnel, with a clean escape hatch between levels.
- **(+)** Reuses the existing model: one IR, two front-ends, deterministic codegen ([ADR-0037](#adr-0037)) for the stubs, deterministic Matching ([ADR-0033](#adr-0033)) for placement — no new runtime semantics.
- **(+)** The Forge/training-engine get a compact, scoreable target: generate declarations (Level 1), emit stubs (Level 2), or optimize either, all over the stable AST.
- **(−)** Two authoring surfaces (TS ↔ Hobo Code) plus two entry levels to keep semantically aligned — enforced by the shared IR + transpiler + the codegen `--check` gate.
- **(−)** Generated-stub quality depends on codegen fidelity (the WIT→TS mapping, [ADR-0037](#adr-0037)); advanced shapes may need hand-tuned emit.
