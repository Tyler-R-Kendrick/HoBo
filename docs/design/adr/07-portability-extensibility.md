# Portability, extensibility, deployment topology & scope — consolidated decisions

> Consolidated ADR decisions for **portability, extensibility, deployment topology & scope**. Each section is one architecture decision; see [`README.md`](./README.md) for the full ADR index.

## ADR-0024
**Portability conformance guarantee ("same Bindle, N clouds").**

### Context
HoBo's core promise — *"write once, deploy to N clouds, unedited; self-host = hosted"* — needs **defensive mechanisms** that keep it from silently eroding: "unedited" needs a formal meaning, the agnostic-core layering invariant needs an enforced check, runtime portability must be proven across ≥2 runtime backends, lock-in must be detectable, runtime/upstream versions need a policy, and self-host/hosted parity must be explicit. A promise without a conformance mechanism degrades to marketing.

### Decision
Make portability a **conformance guarantee** with verifiable mechanisms (each lands as an `NFR`/`FR`/`TR`):
1. **Define "unedited" precisely — and gate it, don't just warn.** Across cloud targets the **`bindle()` definition and** application source (`src/`) are **byte-identical**; only the **`camp()`/`yard()` mapping** and CLI/env parameters may change. But byte-identical is **necessary, not sufficient**: a Bindle can be byte-identical yet still carry single-provider `.with()` or a `.raw(driver => …)` dialect leak (§4) that does *not* run on N clouds. So "portable" is a **gated property over a declared non-portable surface**: the `multi-cloud-shop` E2E deploys an unchanged Bindle to ≥2 providers, asserts identical resource topology + bindings, **and asserts the Bindle's declared non-portable surface (the §4 PortabilityReport) is either empty or wholly satisfied by *every* targeted provider**. A Bindle that uses a single-provider feature is portable **only across the providers that satisfy it** — `can-deploy` refuses a target that doesn't, rather than shipping a byte-identical Bindle that silently fails on cloud N. The unqualified "same Bindle, N clouds" claim holds exactly for Bindles with an empty non-portable set. (NFR-001, TRD §5.1)
2. **Enforce the layering invariant in CI** — a dependency-graph lint gate (e.g. `depcheck`/`madge`) fails the build if `@hobo/core` (or any agnostic package) imports a provider/iac/build package, or if an adapter imports another adapter. The agnostic core cannot leak provider detail. (TR-006, NFR-020)
3. **Prove runtime portability** — at least one example runs unchanged on ≥2 runtime backends (e.g. `runtime-local` and `runtime-postgres`) with only a runtime override, asserting identical lifecycle (replay==live). (TR-012) **Component-host portability is conformance-gated + version-pinned per [ADR-0031](01-architecture-core.md#adr-0031):** the `component-host` is itself a per-Camp port whose claimed hosts must pass the `@hobo/conformance/component-host` suite (deterministic-clock replay, `wasi:*` round-trip, link semantics, capability-handle isolation) and whose kind+version is pinned in the manifest IR. The honest guarantee is **"behaves equivalently with respect to the suite's asserted properties,"** *not* "bit-identically in every observable" — the suite **pins the determinism-relevant host behaviors** (floating-point/NaN canonicalization, fuel/epoch scheduling, and resource-limit semantics) and any host behavior *not* in the asserted set (e.g. wall-clock scheduling jitter, host-specific partial-failure timing) is a **declared, documented non-covered divergence**, not an implied equivalence.
4. **Detect lock-in — and feed it into the §1 gate, not just a warning.** The **PortabilityReport** ([Plan 21](../authoring-resources-wiring.md#plan-21)) emitted with `deployment.Planned` is the Bindle's **declared non-portable surface**: every provider-specific `.with()`, every `.raw(driver => …)` dialect leak, every cross-paradigm-only feature, every static key where federation exists, **and every `external`/adopted dependency** ([ADR-0041](#adr-0041)). `hobo doctor` surfaces each with severity (authoring-time guidance), **and `can-deploy` uses the same report as the §1 gate input** — a member of the non-portable set that a *targeted* provider can't satisfy fails the deploy to that target. Data portability is paradigm-class-scoped: a Bindle is portable *within* a projection-sink paradigm class (relational↔relational, document↔document, …), not across classes ([Plan 32](../data-plane.md#plan-32)/[ADR-0052](03-data-plane.md#adr-0052)). So lock-in is **surfaced** (doctor) *and* **enforced** (the gate refuses an unsatisfiable target), never silently shipped. (FR-014)
5. **Pin upstream + define a version policy** — exact pins for Pulumi Automation API / WASI-WIT / MCP; runtime-port versions are recorded in the manifest IR and are immutable for a Bindle version; upgrades go through an explicit, gated `hobo upgrade` path with a compat/upgrade test in CI. A version-mismatch fails planning with a precise reason. (TR-013) `hobo:*` versioning is pin-and-gate.
6. **State self-host/hosted parity** — self-host and hosted ship the **same code and the same control-plane features** (identity, policy, audit, conformance, observability); the **only** differences are operational (managed multi-region HA, org SSO/RBAC, support). A hosted-gated feature must be explicitly documented and must not silently weaken self-host security. **Parity is over *features + code*, not auto-enforced *posture*:** enforced security posture (e.g. the no-preview-in-prod ceiling, min-provenance-tier) is operator-*configured* policy, so it can differ between a hosted operator and a self-hosting org. To honor "must not silently weaken self-host security," the **safety-relevant deny-ceilings ship default-on in the hardened/`prod` Yard profile** ([ADR-0075](#adr-0075) §5), so a default self-host prod install matches the hosted posture unless an operator explicitly (and auditably) relaxes it. (NFR-013)
7. **The intended provider set is documented but non-limiting.** HoBo names a *seed* set of intended providers/hosts — self-hosted **wasmCloud** (default host, [ADR-0031](01-architecture-core.md#adr-0031)), **Hetzner**, **Cloudflare**, **Vercel**, **AWS/Azure/GCP**, **Fly**, and self-host targets (**Coolify**/k8s/bare-metal) — in the [providers & deploy-targets matrix](../control-plane.md#plan-04). The set is **open**: each is a swappable adapter behind the `CloudProvider`/`component-host`/`IacProvider` ports, the **generation pipeline** generates new adapters on demand ([ADR-0010](03-data-plane.md#adr-0010)), unsupported configs are caught at author time with remediation ([ADR-0033](01-architecture-core.md#adr-0033)), and any backend that passes conformance is first-class. Documenting the seed set names where portability is *validated*; it never caps it.

### Consequences
- **(+)** "Same Bindle, N clouds" and "self-host = hosted" are testable gates (CI lint, ≥2-runtime E2E, multi-cloud E2E, parity tests), and lock-in + upstream churn have explicit detection/isolation requirements.
- **(−)** The CI dep-graph lint and ≥2-runtime E2E add engineering cost and require a second mature runtime backend, and the version-pinning policy adds an upgrade ceremony.

## ADR-0057
**Patchability as a first-class guarantee (distinct from portability).**

### Context
**Portability** ([ADR-0024](#adr-0024)) means the same artifact runs unmodified on N backends. The architecture also affords something portability does not: you can **change HoBo itself** — every engine is behind a port, every seam is an adapter, the Yard is a Bindle, and AI/human edits persist via region-scoped AST mutation ([ADR-0048](03-data-plane.md#adr-0048)). Naming this a guarantee makes the extension seams a *contract* and keeps derivatives trustworthy via the same conformance/signing machinery. **Portability = same artifact runs on N backends; patchability = derive/extend/patch the platform itself, persisted OR ephemeral.**

### Decision
1. **Adopt patchability as a first-class guarantee, distinct from portability.** Definition: *you can derive your own HoBo (swap any engine, add any adapter, fork the Yard) and apply AI/human patches, and a conforming derivative is a trusted, upgradable first-class citizen.* Portability = the user's app isn't locked to a backend; patchability = the platform isn't a black box.
2. **Three pillars** ([Plan 23](../generated-stack.md#plan-23)): **(a) derivative implementations** behind the same WIT ports, distributed as signed Resource Packs/plugins, human- or AI-generated; **(b) enumerated extension seams** (providers/IaC/build, capability providers, runtimes/`component-host`, drivers, engines, Resource Defs/Packs/Profiles, agent-skills, projection sinks, **integration ports** — auth/artifact-repo/issue-tracker/knowledge, [ADR-0073](#adr-0073)) — adding an implementation never edits the core; **(c) patches** in two distinct kinds (below), both region-scoped and provenance-tracked.
3. **Two kinds of patch (inspired by npm `patch-package`).** A patch derives or extends behavior without editing the upstream source outright; HoBo distinguishes *where the change lives*:
   - **Persisted patches** — changes captured into source/artifacts via the region-scoped, format-preserving AST mutation mechanism + signed provenance ([ADR-0048](03-data-plane.md#adr-0048)), conformance-gated and round-trippable + drift-gated ([ADR-0037](01-architecture-core.md#adr-0037)). Durable, reviewable, version-controlled — the patch becomes part of the derivative.
   - **Runtime-instance patches (ephemeral)** — at runtime, agents may apply changes that affect **only the running runtime instance** and are **not persisted to *source control*** (the way `patch-package` overlays a dependency locally without committing to upstream). Each is **scoped to the instance** and **discarded / garbage-collected** unless explicitly **promoted to a persisted patch** (which re-enters the [ADR-0048](03-data-plane.md#adr-0048) region/provenance + conformance path). **"Not in source control" does *not* mean "not replayable" — that distinction is load-bearing for the determinism invariant** (`replay == live state`, [ADR-0021](#adr-0021)/[Plan 11](../data-plane.md#plan-11) invariant #1). So the **full patch content/diff is captured as a durable event** (`derivative.EphemeralPatchApplied{ instance, regions, diff, provenance }`), not merely referenced: an instance's behavior change is therefore **derivable from the log**, so replaying the log **reconstructs the patched instance** and the invariant holds. The patch lives outside the *git/source artifact* (it isn't promoted upstream) while living *inside* the replayable event stream — and conformance asserts replay-of-an-ephemerally-patched-instance reproduces the patched behavior. An ephemeral patch never silently mutates source, and never silently escapes replay.
4. **Conformance is the trust bridge for both guarantees.** The same `@hobo/conformance` suite ([Plan 9](../generated-stack.md#plan-09)) + signing/provenance ([Plan 12](../security-networking.md#plan-12)) that make a *swapped backend* safe (portability) make a *derived implementation* and a *persisted patch* safe (patchability). A persisted patch or derivative that passes conformance is trusted; one that doesn't is rejected. An ephemeral patch is gated by instance-scope + audit, and must pass conformance to be promoted.
5. **Seams are versioned so derivatives survive upstream upgrades.** A long-lived derivative (swapped engine, custom drivers, persisted patches) needs a defined answer for "core ships a breaking WIT-port change" — without one, forks rot or fork permanently. So:
   - **Each extension seam is independently semver-versioned.** Every enumerated seam (a WIT port: `policy-engine`, `contract-engine`, `component-host`, a provider/driver/runtime/projection-sink) carries a semver; a Yard pins the seam versions it requires, and the manifest IR records which seam versions a Bindle uses (proven by its conformance run).
   - **A signed `derivative.json` descriptor** ([Plan 12](../security-networking.md#plan-12)) declares the **core version range** it targets (`core@^1.0.0 <1.1.0`), its **seam implementations + versions** (`policy-engine@2.3.0`, `custom-aws-driver@1.0.0`), and **pinned upcasters** for any persisted patches ([ADR-0048](03-data-plane.md#adr-0048)) — codemods that repair the hand-written/generated regions on a core upgrade.
   - **An `hobo derivative upgrade <from> <to>` ceremony** checks `derivative.json` compatibility (warns on any seam/patch incompatibility), runs the pinned upcasters, **re-runs seam conformance** to prove the upgrade didn't regress a guarantee, and emits an upgrade report. Events: `derivative.UpgradeStarted` · `derivative.UpgradeSucceeded` · `derivative.UpgradeFailed`.
   - **Core releases ship a breaking-change manifest** of the seam/port changes with upcaster hints (*"`policy-engine` gained decision field X — here's the migration"*), so derivative authors write targeted upcasters instead of reverse-engineering the diff. The upgrade is explicit + gated — never a silent auto-rebase of a fork's swapped engines/patches, which is exactly the un-auditable mutation [ADR-0048](03-data-plane.md#adr-0048) rejects. A derivative that re-passes conformance post-upgrade stays a trusted, upgradable first-class citizen.
6. **Never gate patchability behind a paid tier** — consistent with the never-gate-portability stance ([ADR-0024](#adr-0024)); the core is self-hostable and forkable.

### Consequences
- **(+)** A real differentiator (closed PaaS has neither portability nor patchability; raw IaC lacks portability) with the extension seams as a stable, enumerated contract — derivatives, persisted patches, ephemeral patches, and swapped engines all ride one trust bridge (conformance + provenance + audit) and stay maintainable across core releases via semver + signed descriptor + re-run conformance + upcasters + the drift gate.
- **(−)** Ephemeral patches add an instance-scoped lifecycle and a two-part contract (*not in source control*, yet *in the replayable log*), the now-semver-versioned seams become a public surface the core must evolve carefully, and third-party derivative trust needs a signing/attestation chain beyond the basics ([Plan 12](../security-networking.md#plan-12)).

## ADR-0035
**Custom domains & multi-cloud ingress.**

### Context
[Plan 12](../security-networking.md#plan-12) specifies the `gateway` port (TLS termination, routing, traffic-split) and HoBo-managed DNS for *internal* logical endpoints. Custom domains need full treatment, and the genuinely hard, HoBo-specific part is provider-global routing: a Yard is **provider-specific** and holds provider-global networking + global gateways ([ADR-0026](01-architecture-core.md#adr-0026)), so a domain that fronts **multiple Camps** (e.g. `prod-eu`, `prod-us` under one provider's Yard, [ADR-0028](01-architecture-core.md#adr-0028)) — and, across providers, multiple Yards under a Junction ([ADR-0043](#adr-0043)) — raises **who owns `shop.com`, how does traffic route across Camps/clouds, and who issues the cert?** DNS / custom domains belong at the **Yard level (provider-global), with per-Camp overrides** — *not* at the app/Bindle level, since a Bindle is provider-agnostic and carries no provider-global zone. **DNS is high-blast-radius and slow to recover** (propagation/TTL, cache poisoning of a bad change), so every DNS change is treated as a guarded, tested, reversible rollout — never a fire-and-forget write.

### Decision
1. **A custom domain is a Yard-level resource (provider-global), with per-Camp overrides — never app/Bindle-level.** `domain("shop.com").routes(api)` is owned at the **Yard**, which holds the provider-global networking + global gateway and runs the provider's control plane ([ADR-0026](01-architecture-core.md#adr-0026)). It is declared IfC-style, **fronts the Yard's Camps**, and lets a Camp **override** the provider-global record set (e.g. a region-specific target or cert adapter). It is backed by a **`dns` capability** + the **`gateway`** port ([Plan 12](../security-networking.md#plan-12)). One provider-global domain, N Camps with per-Camp overrides. Cross-cloud, a domain fronting Camps in **different providers' Yards** is federated by the Junction ([ADR-0043](#adr-0043)); the zone is never pushed down to the agnostic Bindle.
2. **Routing across Camps is policy-driven DNS.** The domain carries a routing policy — **`failover`** (active-passive, health-checked), **`weighted`** (canary/split), **`latency`/`geo`** (nearest Camp), or **`cost`** (cheapest healthy backend by effective marginal cost, driven by the **Dispatcher** [ADR-0071](01-architecture-core.md#adr-0071) — **only for `active-active-eventual`/`pinned`-replica resources** [ADR-0040](01-architecture-core.md#adr-0040); hysteresis-bounded per [ADR-0071](01-architecture-core.md#adr-0071) §6) — programmed through a **provider-agnostic `dns` capability** at the Yard, with per-Camp overrides. **The cost-routing eligibility check is per-route, not per-domain.** A domain fronts *Camps*, and a Camp typically hosts many resources of mixed replica classes, so "refuse cost-routing on a single-writer resource" is enforced by a **per-route reachability analysis at `can-deploy`** (`hobo doctor` author-time): if *any* resource reachable through a cost-routed route is single-writer ([ADR-0040](01-architecture-core.md#adr-0040)), that route is refused cost-routing (cost-routing a write-home request just adds a hop) — only routes whose entire reachable set tolerates cost-routing are eligible. A domain fronting a mix routes its single-writer paths home and may cost-route only the eligible paths; `can-deploy` asserts no single-writer route is cost-routed. It reuses the env-group saga ([ADR-0028](01-architecture-core.md#adr-0028)), the blue/green gateway flip + health signals ([Plan 5](../reliability-observability-cost.md#plan-05)), and records each routing decision as an event (auditable "why did traffic go to `prod-eu`"). HoBo does **not** operate a global data-plane LB.
3. **No DNS change promotes without passing an automated validation gate (mandatory).** Every DNS/custom-domain change is **tested and validated *before* promotion** — the planner stages the record set and a gate must pass: **resolve checks** (the new records resolve to the intended targets from multiple resolvers/vantage points), **propagation checks** (TTL-aware confirmation the change is visible, not just written), **ACME/challenge validation** (the cert challenge passes for the new state), and **endpoint health checks** (each target Camp's gateway answers healthy through the new path). A failed check **blocks promotion**, emits the failure, and leaves the live zone untouched. There is no path that mutates the live record set ahead of these checks.
4. **Failover/cutover rollouts are health-checked, staged, and auto-rolling-back — with recovery bounded by TTL, stated honestly.** A routing/cutover change is rolled out **staged / canary** — shift a small weight or a single resolver class first, watch health + error/latency signals against the pre-cutover baseline, then widen only on green. **Automatic rollback on regression**: if post-cutover health or SLOs regress past threshold, HoBo **initiates** a revert to the last-known-good record set without operator intervention and emits the rollback. **But DNS reverts are subject to the same propagation/TTL lag as the cutover** — a record already cached resolves to the bad target until its TTL expires — so the auto-rollback's **effective RTO is ≥ the max cached TTL**, not instant. Because of this, **low record TTLs staged *before* any cutover begins are a precondition gate** (the planner lowers + propagates TTLs and waits out the old TTL before shifting weight), so the revert window is bounded and small. Active-passive `failover` is itself health-gated (traffic moves only to a target proven healthy). This reuses the blue/green gateway flip + health signals ([Plan 5](../reliability-observability-cost.md#plan-05)).
5. **Certs are ACME DNS-01 by default, issued + rotated by Identity (secretless).** Because HoBo controls the zone, **DNS-01** works across any cloud, including wildcards and multi-Camp; certs are issued + auto-rotated by Identity ([Plan 6](../ai-native-agent-auth.md#plan-06)/[Plan 21](../authoring-resources-wiring.md#plan-21)) with **no static cert secret** ([ADR-0027](02-identity-security.md#adr-0027)). **Provider-managed certs** (ACM / App Service / Google-managed) are an **opt-in per-Camp adapter** when a provider's LB requires its own.
6. **Ingress depth stays layered:** the `gateway` does TLS termination + routing + traffic-split + provider `.with()` WAF/rate-limit/DDoS; the Yard-level `domain` sits above it (provider-global, with per-Camp overrides), routing across the Yard's Camps.
7. **Per-app-tenant routing reuses this for multi-tenant apps** ([Plan 50](../security-networking.md#plan-50)/[ADR-0079](02-identity-security.md#adr-0079)): a tenant is reachable by **subdomain** (`acme.app.com`, wildcard cert via DNS-01), **custom domain** (the tenant's own domain, a tenant-scoped `domain` resource), or **path** (`app.com/t/acme`); the gateway resolves the tenant into **`ctx.tenant`** (and, for siloed/region-pooled tenants, selects the tenant's Camp/region) before any handler runs — no new ingress mechanism, just tenant resolution over the existing `domain`/`dns`/`gateway` stack.
8. **No-friction microfrontends, CORS, and cert auto-renewal — provider-API-driven.** Composing **vertical microfrontends** is a one-line declaration — `domain("shop.com").mount("/checkout", checkoutUi).mount("/account", accountUi)` (or per-subdomain) routes each vertical to an independent deployable UI behind the one domain; the `gateway` does the path/host routing and each vertical ships on its own cadence. **CORS is first-class config** on the `domain`/`gateway` (`allowOrigins`/`methods`/`credentials`), **default-closed and auto-derived from the declared verticals' origins** so cross-vertical calls work without hand-tuning. **Certs auto-renew and auto-rotate with no operator action**: the ACME DNS-01 path (point 5) renews ahead of expiry, and the **provider-managed-cert adapter renews/rotates through the provider's API** (ACM / App Service / Google-managed) — either way certificate expiry is a HoBo-owned obligation (renewed early, surfaced + escalated via [A2H](02-identity-security.md#adr-0082) only if renewal fails), never a manual ticket.
9. **Events:** `domain.Registered` · `domain.ValidationStarted` · `domain.Validated` (resolve + propagation + ACME + health gate passed) · `domain.ValidationFailed` (which check failed) · `domain.CertIssued` · `domain.CertRotated` · `domain.CutoverStarted` · `domain.RoutingChanged` (policy decision + chosen target Camps) · `domain.RolledBack` (auto-revert to last-known-good + reason).

### Consequences
- **(+)** A genuine **multi-cloud ingress** story — one domain routes across clouds with failover/weighted/geo policies — where DNS changes are **safe by construction** (nothing promotes until resolve/propagation/ACME/health checks pass; cutovers are staged with automatic rollback), reusing the provider-global Yard topology, env-group saga, gateway flip + health, and secretless Identity, with ACME DNS-01 giving portable, wildcard-capable, auto-rotated certs with no static secret.
- **(−)** DNS-based routing has propagation/TTL latency on failover (seconds–minutes) vs an anycast LB's instant flip, and the pre-promotion validation gate adds latency and is ongoing per-provider equivalence-class work the `dns` capability must be conformance-covered for.

## ADR-0036
**Air-gapped / sovereign Yard mode.**

### Context
The **HoBo Relay** ([Plan 25](../platform-engineering.md#plan-25)) dials a hosted Yard over outbound 443 and keeps credentials + Executors inside the customer network — but it **assumes a reachable hosted Yard**. A classified/regulated/sovereign environment has no such path: no egress to a hosted control plane, the public Registry, public ACME, or hosted AI models. HoBo is self-hostable (the Yard is a Bindle, [Plan 4](../control-plane.md#plan-04)), the generation pipeline runs no-egress ([ADR-0023](02-identity-security.md#adr-0023)), and the in-boundary pieces exist (local `embed` — [ADR-0034](03-data-plane.md#adr-0034); private-ACME-capable certs — [ADR-0035](#adr-0035); in-boundary KMS — [ADR-0027](02-identity-security.md#adr-0027)). The air-gap profile ties them together with an **honest matrix** of what works, degrades, or needs a substitute with zero egress.

### Decision
1. **Air-gap is a first-class self-hosted Yard profile** — the entire control plane (Yard + Registry + Identity + Executors + runtime + optional models) runs **inside the boundary with zero egress**. The HoBo Relay remains the *connected-private* answer; this profile is the *disconnected/sovereign* answer. The design ships a **capability-degradation matrix** (below).
2. **Artifacts enter via signed offline bundle import** (`hobo registry import <bundle>`): a curated bundle of provider plugins, Capability Manifest, Resource Packs, base images, and optional model weights, each carrying **SLSA-style provenance + conformance reports**, **verified in-boundary against the same trust boundary** as the live Registry (signature + provenance + conformance). Transfer is one-way-friendly (sneakernet / data diode); the in-boundary Registry serves the mirror — **no live crawl** of external `/.well-known/capability-manifest/`. **What this catches, and what it can't (stated, not overclaimed):** verification refuses a bundle that *fails* signature/provenance/conformance, but a signature is not a guarantee of benignity — a **validly-signed-but-malicious** bundle (compromised signing key / insider), a **forged conformance report** from the same compromised pipeline, or a **rollback to an older signed-but-vulnerable** bundle would all pass naïve signature checks, and zero-egress means **no live CRL/OCSP/transparency-log reachability**. So bundle import adds three in-boundary defenses: (a) **offline signed revocation material** (a signed revocation list / key-expiry imported *with* the bundle and checked at import — a key compromised before the bundle was cut is caught); (b) **monotonic anti-rollback** — `registry import` rejects a bundle whose version/build-timestamp is older than the installed one for the same artifact, unless an operator explicitly force-downgrades (audited); (c) a **transparency-log inclusion proof** carried in the bundle (the artifact was publicly logged at production time), verified offline against a pinned log root. Each is a named gate on `registry.BundleImported`.
3. **In-boundary trust roots + local models, graceful degradation.** Identity issues SVIDs locally (already in-boundary); custom-domain certs use an **internal CA / private ACME** ([ADR-0035](#adr-0035)); secrets use **in-boundary KMS/HSM** ([ADR-0027](02-identity-security.md#adr-0027)); `embed`/generation pipeline/`"use training"` use **local in-boundary models when provisioned, else degrade gracefully** (generation pipeline → human-authored providers only; `"use training"` → static implementation; `embed` → BYO vectors). Telemetry/live-evals stay in-boundary (local OTel collector); **no phone-home**.
4. **The deterministic core never needs a model or egress.** Deploy, Matching ([ADR-0033](01-architecture-core.md#adr-0033)), migration ([ADR-0032](03-data-plane.md#adr-0032)), and routing ([ADR-0035](#adr-0035)) are pure/local, so an air-gapped deploy works fully regardless of AI availability.
5. **Event:** `registry.BundleImported` (signed-bundle import + verification result) — a supply-chain audit fact.

#### Capability-degradation matrix
| Capability | Normal (connected) | Air-gapped substitute |
|---|---|---|
| Registry (Capability Manifest / plugins / packs) | crawl `/.well-known/capability-manifest/` | **signed offline bundle import** → in-boundary mirror |
| Container/component images | public registry pull | mirrored into an in-boundary OCI registry (bundle) |
| TLS certs (custom domains) | ACME → Let's Encrypt | **internal CA / private ACME** (or provider-managed in-boundary) — [ADR-0035](#adr-0035) |
| Identity / SVID | issued by the Yard | unchanged — already in-boundary |
| Secrets | provider KMS | **in-boundary KMS/HSM** — [ADR-0027](02-identity-security.md#adr-0027) |
| `embed` (search) | hosted embedding API | **local embedding model**, else BYO vectors — [ADR-0034](03-data-plane.md#adr-0034) |
| AI generation | hosted LLM | **local LLM**, else human-authored providers only |
| `"use training"` | hosted LLM + telemetry | **local LLM**, else static impl; live-evals in-boundary |
| Telemetry / live-evals | hosted/3p sinks | **in-boundary OTel collector**, no phone-home |
| Deploy / match / migrate / route | — | **zero egress, no model needed — always works** |

### Consequences
- **(+)** A real **sovereign/regulated** story — a zero-egress Yard with a documented substitute for every external dependency, deploys working fully without any model or network — reusing self-host, the no-egress generation pipeline sandbox, in-boundary KMS, local `embed`, and private ACME; bundle import keeps the **same supply-chain trust boundary** plus three air-gap-specific defenses (offline revocation, anti-rollback, transparency-inclusion proof).
- **(−)** Operating an air-gapped install adds toil (curating signed bundles, an internal CA + in-boundary model, manual update cadence), and AI features are reduced unless the operator provisions a capable local model (explicit in the matrix). Air-gap is a **single in-boundary Yard**; multi-Yard **federation** is the Junction's concern ([ADR-0043](#adr-0043)).

## ADR-0041
**Migration & onboarding (adopt-in-place).**

### Context
HoBo has the *primitives* for adoption — the **Pulumi Automation API** as primary IaC ([ADR-0006](./README.md)), **CDKTF import-only** ("read existing stacks, don't author new", [Plan 4](../control-plane.md#plan-04) §IaC adapters), and OpenTofu state backends. The **onboarding journey** on top of them moves an existing app/infra estate onto HoBo *incrementally*, without a greenfield rewrite. This is adoption-critical: teams have Terraform/Pulumi estates, Lakebed Capsules, and FaaS deployments; HoBo must meet them where they are.

### Decision
1. **`hobo import` adopts existing infra/code in place.** A command family reads an existing estate into HoBo's resource graph: `hobo import terraform|pulumi|opentofu <state>` (via the existing CDKTF import-only + Pulumi Automation API), `hobo import lakebed` (Capsule→Bindle mapping), `hobo import faas` (wrap existing functions). Imported resources become **`adopted` existing nodes** in the Planner DAG — managed by id/state, **never destroyed/recreated on import** (drift-detect only, [Plan 5](../reliability-observability-cost.md#plan-05)).
2. **Brownfield coexistence (strangler-fig) — with the trust-boundary cost made first-class, not just a doctor hint.** HoBo can **reference un-managed external resources** via an **`external` resource kind**, so a half-migrated app works (a HoBo-managed `api` binds to a `db` still living in Terraform). Teams migrate incrementally and strangle the old stack over time; nothing is big-bang. But an `external` resource sits **outside HoBo's equivalence-class/conformance boundary and outside brokered identity**, so a Bindle depending on one is neither fully portable ([ADR-0024](#adr-0024)) nor necessarily secretless (its credential may be a static key HoBo didn't broker). So `external` dependence is a **first-class entry in the §4 PortabilityReport non-portable surface ([ADR-0024](#adr-0024) §4)** *and* a **counted exception in the zero-secret audit** ([ADR-0021](#adr-0021)) — surfaced and severity-scored, not merely a `hobo doctor` "should-flag." It is **excluded from the portability conformance assertion** (the guarantee is stated over the managed surface), so a brownfield app's portability claim is honest about the un-managed edge rather than quietly violated.
3. **Importer breadth via the generation pipeline.** Ship **reference importers** (Terraform/Pulumi/OpenTofu state, Lakebed Capsule, generic FaaS) with documented mappings; an importer is a transform the **generation pipeline can generate** ([Plan 23](../generated-stack.md#plan-23)) for a new source, gated by a **round-trip/idempotence conformance test** (import → plan → no-op diff) — so onboarding breadth isn't human-bottlenecked, exactly like provider generation.
4. **Event:** `resource.Adopted` (an existing resource brought under management + its source/provenance), distinct from `resource.Provisioned`.

### Consequences
- **(+)** Existing TF/Pulumi/Lakebed/FaaS estates move onto HoBo **incrementally**, adopting in place and coexisting with un-migrated infra, reusing the Pulumi Automation API + CDKTF import-only, drift detection, and the generation pipeline + conformance boundary (the new surface is the `import` command family, an `external`/`adopted` resource kind, and one event) — strengthening positioning vs Lakebed and raw IaC ([Plan 17](../vision.md#plan-17)).
- **(−)** Adopting heterogeneous estates means importer mapping fidelity is ongoing work, and `external` references span a trust/lifecycle boundary HoBo doesn't fully control — a first-class PortabilityReport + zero-secret-audit exception so the portability/secretless guarantees stay honest about the brownfield edge.

## ADR-0043
**The Junction: cross-cloud / hybrid federation of provider-specific Yards.**

### Context
A **Yard is provider-specific** ([ADR-0026](01-architecture-core.md#adr-0026)): it groups Camps under **one** provider and owns that provider's cross-Camp policy, provider-global networking (vWAN), and global gateways (Azure Front Door). Multi-region *within a provider* is several Camps under one Yard ([ADR-0028](01-architecture-core.md#adr-0028)) — no second Yard. But the moment an app spans **more than one provider** (or mixes cloud + on-prem), it spans **more than one Yard**, and something has to connect those provider-specific Yards across the cloud boundary. That is the **Junction**: the first-class, primary mechanism for cross-cloud / hybrid. The Junction is the **broadest scope** — `Bindle ⊂ Camp ⊂ Yard ⊂ Junction` — and a multi-cloud app is, by definition, **several Yards under one Junction**. Cross-cloud is a normal, expected scenario, so the connective tissue is a named first-class concept, not an afterthought smuggled into a control plane.

### Decision
1. **The Junction is the cross-cloud / hybrid scope — the broadest scope.** `Bindle ⊂ Camp ⊂ Yard ⊂ Junction` ([ADR-0026](01-architecture-core.md#adr-0026)). A Yard is one provider's stack; a **Junction connects provider-specific Yards** so an app can span clouds and on-prem. **A multi-cloud / hybrid app = several Yards under one Junction** — the ordinary shape of a cross-provider deployment, not an edge case.
2. **The Junction federates trust + signed artifacts + cross-cloud policy across Yards — it is not a shared-state controller.** Thematically, a junction is where independent rail lines meet: provider-specific Yards interconnect as peers, no line subordinate to another. A Junction federates three things and **infers a fourth — the cross-cloud connectivity plane — from its members' manifests**, reusing mechanisms HoBo already has:
   - **Identity trust — with explicit establishment, rotation, and *fast* revocation** (not a static cross-config). Cross-Yard SVID/OIDC trust is **short-TTL federation metadata** exchanged under an agreed root (the same OIDC federation HoBo does for providers, [Plan 6](../ai-native-agent-auth.md#plan-06)), so a principal authenticated in the AWS Yard is recognized by the Azure Yard — but because a peer Yard whose trust root A still honors could **forge principals *into* A** (worse than merely ignoring its own policy rules), revocation must be quick. **The revocation has a specified propagation contract** (since the Junction holds no shared mutable state, "drop a peer" needs a defined channel): the **revoking Yard publishes a signed `junction.TrustRevoked`** that every member Yard **pulls/receives and applies to its own federation-trust projection**, ordered by the revocation's monotonic issue sequence (a later revoke supersedes an earlier re-establish). Crucially, **trust is *leased*, not ambient: a peer's federation metadata is valid only while its short-TTL lease is fresh, so a member that cannot confirm trust freshness with the root within the TTL (a partition) fails *closed* — it stops honoring that peer's principals** rather than trusting a stale-but-unrevoked entry. So the worst-case forge window is bounded by **`min(time-to-receive-the-revoke, the trust-lease TTL)`**, and that **TTL is a hard NFR** (e.g. ≤ 5 min, [ADR-0021](#adr-0021)). A chaos test ([ADR-0047](02-identity-security.md#adr-0047)) asserts a revoked peer's forged principals are rejected within the bound **even under a partition between the member and the revoking party**. This is the mechanism [ADR-0074](02-identity-security.md#adr-0074) §6's cross-Yard governance (and "scope the estate to attested Yards under a shared root") depends on — a specified establish/rotate/revoke contract.
   - **Cross-cloud policy** — shareable **signed policy packs** ([Plan 29](../contracts-policy-flags.md#plan-29)) propagate across the Junction, so policy spanning the provider boundary is expressed once and enforced by each Yard. This is also how **org governance deny-ceilings** ([ADR-0074](02-identity-security.md#adr-0074)) — RBAC + the mandatory deny-ceiling over HoBo's own control-plane surface — stay consistent across an estate's Yards without a new top-level scope noun.
   - **Registry / signed artifacts** — certified providers/packs flow between Yards via the **signed-bundle/mirror** mechanism ([ADR-0036](#adr-0036)).
   - **Cross-cloud connectivity (inferred, not centrally controlled)** — the Junction folds its members' **Yard manifests** (each Yard's exposed endpoints/domains + the cross-Yard links its Bindles need) into the cross-boundary graph and **infers the connectivity plane** the same way Matching realizes any resource ([Plan 25](../platform-engineering.md#plan-25)): the connectivity tier (native peering → PrivateLink/PSC → overlay mesh → public+mTLS, [Plan 12](../security-networking.md#plan-12)) and the `hobo:dns` rules ([ADR-0035](#adr-0035)). Because the Junction holds no shared state, it **emits each Yard its own half of the plan**, which that Yard realizes under its own control plane (the Azure Yard provisions the Azure side of a PrivateLink + its DNS records; the AWS Yard provisions its side). The inference is recorded as `junction.ConnectivityInferred`; each half is an ordinary resource event in that Yard's own log. The Junction decides *what* must connect; each Yard decides and owns *how* on its side — so residency and the peer/no-controller invariant stay intact.
   Each Yard keeps its **own event log + control plane + data** — the Junction is **trust + signed-artifact + cross-cloud-policy federation plus inferred cross-cloud connectivity (each Yard realizing its own half), never shared mutable state and never a super-controller**. A cross-Yard operation is a *federated request* (authn via federated identity, authz by the **target** Yard's own policy), with **data residency preserved** (nothing centralizes).
3. **The Junction is peer federation, not a hierarchy.** No assumption of a single global trust root: identity/policy/registry are federation-ready by construction — policy packs + registry bundles signed/portable, events `tenant`-scoped. A cross-cloud app declares its member Yards (e.g. an AWS Yard + an Azure Yard + an on-prem Yard) under one Junction; the Junction wires their trust, shares the cross-cloud policy, and brokers federated requests, but never reaches into a Yard's state. The Junction's events are `junction.YardJoined` · `junction.TrustEstablished` · `junction.ArtifactShared` · `junction.PolicyPropagated` · `junction.ConnectivityInferred` · `junction.YardLeft`.

### Consequences
- **(+)** Cross-cloud / hybrid has a clean first-class home — a multi-cloud app is **several provider-specific Yards under one Junction** (the broadest scope) — reusing OIDC federation, signed policy packs, and the signed-bundle mechanism with no new control-plane machinery, so each provider's Yard stays self-contained, single-provider deployments carry zero federation overhead, and data residency is preserved (peer, not central).
- **(−)** A peer federation has no single global view/governance point — cross-cloud policy conflicts between Yards must be reconciled by agreement, not a central authority (acceptable, and the point, for residency + sovereignty).

## ADR-0062
**Registry distribution: publish/discover/install/trust over signed, certified artifacts.**

### Context
HoBo has every primitive distribution needs — a Registry, signed Resource Packs, `@hobo/conformance`, provenance, and MCP — across several plans. A unifying lifecycle keeps third-party/community distribution from staying ad-hoc. The risk to avoid: distribution that becomes a lock-in lever, contradicting the portability guarantee that is HoBo's core promise. **Monetization is out of scope** — HoBo is an AI-native meta-cloud, not a commerce product ([ADR-0064](#adr-0064)); this is **Registry distribution**, not a storefront.

### Decision
1. **Registry distribution is a governed index + lifecycle over existing signed/certified artifacts**, not new infrastructure or new artifact types. Listings = providers / Resource Packs / policy packs / agent-skills / runbooks / Hobo-Code modules / guardrails+model cards / **the scope objects themselves — Bindles, Camps, Yards, Junctions**. A **scope listing** is an npm package or a structured git repo that *exports a constructed scope object / factory* ([ADR-0011](01-architecture-core.md#adr-0011)) — signed + certified like any listing, imported via `npm`/`git` or `hobo add` and bound by Matching — so an org distributes a **preconfigured Camp/Yard/Junction** or a **side-loaded Bindle** (a prebuilt app component) exactly as it ships a provider.
2. **Publish = sign + conformance-certify + provenance** ([Plan 6](../ai-native-agent-auth.md#plan-06)/[Plan 12](../security-networking.md#plan-12)/[Plan 9](../generated-stack.md#plan-09)/[Plan 23](../generated-stack.md#plan-23)) — the same trust boundary every adapter crosses; uncertified ⇒ unlisted (`listing.Published`/`Certified`).
3. **Discover is capability-indexed and agent-drivable** (WIT port + Matching criteria + region/classification), surfaced via MCP so the generation pipeline/agents can install as part of planning.
4. **Install = `hobo add`, bound by Matching** ([Plan 25](../platform-engineering.md#plan-25)) — installing makes an artifact *available* to deterministic selection, never forces its use; air-gap installs via signed offline bundle ([ADR-0036](#adr-0036)).
5. **Trust = provenance tier + publisher identity + ratings** (a composite derived from facts; policy packs can require a minimum tier). **Portability is never gated** ([ADR-0024](#adr-0024)): conformance, ports, import/export, and the swap-for-an-equivalent escape hatch are always free and open; the generation pipeline guarantees an equivalent can always be generated. **No monetization** — Registry distribution carries no commercial tiers and no `billing` port ([ADR-0064](#adr-0064)).
6. **Yank has a decided lifecycle (the security-response path other ADRs rely on).** A listing version moves `Certified → Yanked` (`listing.Yanked`, compromised/broken/CVE/regressed-Capability-Spec) by its **publisher or a Yard security-policy admin** ([ADR-0074](02-identity-security.md#adr-0074)). Propagation to **already-deployed Sets is not silent and not a forced rewrite**: a yank **(a) immediately blocks the yanked version from any *new* selection/redeploy** at `can-deploy` (a planning hard-fail with remediation: pick a non-yanked version or a Matching equivalent), **(b) flags running Sets that pin it** as carrying a yanked artifact (`hobo doctor` + an incident-class signal, [Plan 40](../operators-sre.md#plan-40)), and **(c) for a `severity: critical` yank, raises a remediation obligation** ([Plan 29](../contracts-policy-flags.md#plan-29)) that the SRE operator drives to a gated migration — never force-mutating a running deployment out from under its owner, but not leaving a critical vuln silently deployed either. The operator may set a per-policy override (e.g. "block redeploy but don't auto-page on `low`"). This is the concrete mechanism [ADR-0075](#adr-0075) §6 cites for a regressed Capability Spec.
7. **A curated catalog is a trust-tiered listing set, not a new system.** A Yard — including the **hosted HoBo cloud** — can publish a **pre-approved catalog**: a named, policy-pinned set of listings (providers, Camps/Yards/Junctions, side-loaded Bindles, packs) it vouches for at a given provenance tier (point 5). App devs and platform engineers deploy *from* the catalog with no per-item approval; a policy pack can **require** that production select only pre-approved listings ([ADR-0074](02-identity-security.md#adr-0074)). The hosted cloud ships a default pre-approved catalog so a Bindle can deploy through it with zero platform setup; a self-hosted Yard curates its own. Curation is `listing.Approved`/`listing.Revoked` over the same lifecycle — no separate store.

### Consequences
- **(+)** Operationalizes the marketplace with almost no new machinery — a `listing.*` lifecycle + capability index over already-signed/certified artifacts — with fact-derived trust (provenance tier + conformance + identity) so enterprises govern their own supply chain via policy, and the never-gate-portability invariant enforced structurally so the marketplace can't become lock-in.
- **(−)** Curation/moderation and a polished storefront UX are real product work, yank propagation to already-deployed Sets carries operator judgment in the per-severity policy, and a vibrant third-party ecosystem raises the stakes on conformance-suite quality.

## ADR-0042
**Local-dev fidelity (simulate / mock / Camp-only).**

### Context
HoBo's DX promise is a fast, offline inner loop (`npx hobo new` → `hobo dev`, no cloud — [Plan 7](../developer-experience.md#plan-07)) where the agnostic path runs locally. But "works locally" is only valuable if it *predicts* prod. Some behaviors can be reproduced faithfully on a laptop; some can't (real cloud IAM, cross-cloud mTLS, provider quotas); and conflating them turns a green local run into a false promise. This needs an explicit classification + a way for developers to know which is which.

### Decision
1. **Classify each prod behavior by "does a wrong local answer hide a real bug?"** — **simulate** (high-fidelity local equivalent) the *correctness-determining* behaviors; **mock** (honest seam) the *environmental* ones that can't be real locally; **defer to a Camp** the *irreducibly-real* ones. (See the matrix below.)
2. **Fidelity is labeled, and `hobo verify` splits local vs Camp checks.** Each capability reports its local fidelity — `real | simulated | mocked | camp-only`; `hobo dev` surfaces it; the **conformance suite** ([Plan 9](../generated-stack.md#plan-09)) tags every check `local` or `camp`. `hobo dev` runs the `local` checks (all simulate/real behaviors pass offline); a Camp run runs the `camp` checks. **`hobo verify` will not claim prod-readiness for behaviors that are mocked-only** — it reports coverage = `local ∪ camp` and flags "this needs a Camp test." The fidelity gap is explicit, never silent.

#### The fidelity matrix
| Prod behavior | Local fidelity | Why |
|---|---|---|
| Determinism / replay | **simulate (real)** | `runtime-local` runs the real engine; `replay == state` is the core test ([Plan 2](../sdk-api.md#plan-02)/[Plan 9](../generated-stack.md#plan-09)) |
| `.allow()` capability denials | **simulate (real)** | wasm deny-by-default is real locally ([Plan 20](../wasm-runtime-wit.md#plan-20)) — an un-linked call fails identically |
| Auth/ABAC + policy decisions | **simulate (real)** | the policy engine + agent/end-user auth run locally ([Plan 29](../contracts-policy-flags.md#plan-29)/[Plan 6](../ai-native-agent-auth.md#plan-06)/[Plan 6](../ai-native-agent-auth.md#plan-06)) |
| `can-deploy` / contracts / evals | **simulate (real)** | the Gatekeeper runs locally over the same graph ([Plan 29](../contracts-policy-flags.md#plan-29)/[Plan 23](../generated-stack.md#plan-23)) |
| Resource interfaces (db/kv/bucket/queue) | **simulate** | local equivalents (containerized Postgres, in-mem queue, local object store) — same agnostic client ([Plan 7](../developer-experience.md#plan-07)) |
| Embedding / search | **simulate** | local embed model + pgvector/FTS ([ADR-0034](03-data-plane.md#adr-0034)) |
| Cloud IAM (real provider roles) | **mock** (honest seam) | can't mint real AWS/Azure IAM locally; the `.allow()`→IAM mapping is unit-tested ([Plan 9](../generated-stack.md#plan-09)) |
| Provider latency / egress / cost | **mock** | environmental; the cost/latency *model* is exercised, real figures need a Camp ([Plan 5](../reliability-observability-cost.md#plan-05)) |
| Secrets backends (KMS / Key Vault) | **mock** | local secret stub; the real broker/KMS is Camp-only ([Plan 21](../authoring-resources-wiring.md#plan-21)) |
| Cross-cloud mTLS handshake | **camp-only** | needs two real providers + SVID federation ([Plan 12](../security-networking.md#plan-12)) |
| Real quotas / runaway-spend limits | **camp-only** | provider/plan limits are real-environment ([ADR-0039](02-identity-security.md#adr-0039)) |
| Provider drift / failure modes | **camp-only** | only a real provider exhibits real drift ([Plan 5](../reliability-observability-cost.md#plan-05)) |

### Consequences
- **(+)** "Works locally" is a *bounded, honest* promise — correctness-determining behaviors real locally, environmental ones clearly mocked, the rest explicitly Camp-gated with `hobo verify` enforcing the distinction — reusing the conformance suite + `hobo verify` (new surface is a per-check `local|camp` tag + a per-capability fidelity label) and aligning with the air-gap work ([ADR-0036](#adr-0036)).
- **(−)** Maintaining the matrix + labels as capabilities evolve is ongoing discipline (a mislabeled capability re-introduces the false-promise risk), and mocked behaviors still need a Camp run before prod confidence.

## ADR-0073
**Swappable integration ports: identity, artifacts, work-tracking & knowledge.**

### Context
HoBo's whole model is **ports over platforms** — a capability is a WIT port, backends are swappable adapters, Matching/the Dispatcher consider **only the registered** ones ([ADR-0033](01-architecture-core.md#adr-0033)/[ADR-0071](01-architecture-core.md#adr-0071)), credentials are **secretless-brokered** ([ADR-0027](02-identity-security.md#adr-0027)), decisions are **policy-gated** ([Plan 29](../contracts-policy-flags.md#plan-29)), adapters are **conformance-gated + auto-generatable** ([Plan 9](../generated-stack.md#plan-09)/[ADR-0010](03-data-plane.md#adr-0010)), and **portability is never gated** by one backend ([ADR-0024](#adr-0024)). The meta-cloud's *external touchpoints* — who authenticates, where build artifacts live, where work is tracked, where knowledge lives — follow the same pattern, not hard-wire a vendor. End-user **auth** is such a port ([ADR-0038](02-identity-security.md#adr-0038)). The scope guard ([ADR-0064](#adr-0064)) applies: these are **operational integrations**, not app-business/SaaS functions — work-tracking/knowledge are the surface the **Operator Agents** ([Plan 40](../operators-sre.md#plan-40)) drive (and that app code may also call, like `notify`), never a billing/CRM-style product feature.

### Decision
1. **Integration ports are a uniform category — port + default adapter set, only-registered-considered.** Each external touchpoint is a WIT port with a named default adapter set; Matching/the Dispatcher select among **only the adapters the developer/platform registered**; all are secretless-brokered ([ADR-0027](02-identity-security.md#adr-0027)), policy-gated ([Plan 29](../contracts-policy-flags.md#plan-29)), conformance-gated + auto-generatable ([Plan 9](../generated-stack.md#plan-09)/[ADR-0010](03-data-plane.md#adr-0010)), and **never gate portability** ([ADR-0024](#adr-0024)). Adding one never edits app code.
2. **Auth (`hobo:auth`) joins the uniform integration-port category.** The federate+verify port and **its default adapter set live canonically in [ADR-0038](02-identity-security.md#adr-0038)** (WorkOS/Auth0/Supabase Auth/Entra + Google/GitHub/Clerk/customJwt + dev built-in) — this ADR does not re-list them; it places auth under the same swappable-port rules as the others. **IdP-swap safety:** swapping the IdP adapter on a live Yard **invalidates prior-issuer sessions** (force re-auth; a token from the old issuer's JWKS is rejected, not silently honored), and the **claims→roles/tenancy mapping is an explicit, versioned, conformance-tested part of each IdP adapter** (group shapes differ across WorkOS/Entra/etc.) so a swap can't silently drop or remap the claims that populate `subject.roles` ([ADR-0074](02-identity-security.md#adr-0074)); the swap emits an auditable governance fact.
3. **Artifact repository (`hobo:artifact-repo`) — new configurable port.** The package/artifact repositories HoBo **builds against and publishes to**: default adapters **npm · NuGet · PyPI · OCI** (+ Maven/cargo/RubyGems). It serves dependency **pulls** (build inputs) and **publishes** outputs — language packages and the **component OCI images** `@hobo/componentize` produces ([Plan 20](../wasm-runtime-wit.md#plan-20)). Configurable per Camp/Yard; **mirrorable for air-gap** (reuses the [ADR-0036](#adr-0036) signed-bundle mirror); **SLSA provenance on publish** ([ADR-0010](03-data-plane.md#adr-0010)); creds brokered. **Integrity gates before cost — always.** A pull is **digest-pinned + signature/SLSA-provenance verified against the trust boundary *first*** ([ADR-0023](02-identity-security.md#adr-0023)/[ADR-0062](#adr-0062)); only **among already-verified-identical** artifacts may the **Dispatcher** ([ADR-0071](01-architecture-core.md#adr-0071)) cost/latency-tie-break across mirrors. **Cost never selects an unverified artifact** — "cheapest mirror" cannot become a dependency-substitution vector. **The digest is the selection key, which closes dependency-confusion:** when registered mirrors resolve the same logical `name@version` to **different digests** (namespace shadowing / a poisoned mirror), that is a **hard failure — never a cost tie-break** (cost only ever breaks ties among byte-identical digests); the build fails closed with the conflicting digests surfaced, so a cheaper mirror serving a *different* artifact for the same coordinate is rejected, not silently preferred. Conformance/CI asserts a digest mismatch across mirrors for one coordinate aborts the resolve.
4. **Issue trackers + project knowledge — named, auto-generatable extension seams (operator-facing), not fully specified this round.**
   - **`issue-tracker`** — default adapters **JIRA · GitHub Issues · Linear**. The surface the **Crew** drives: the SRE syncs an **Incident** ([ADR-0058](03-data-plane.md#adr-0058)) → a ticket, postmortems-by-replay open tickets, the SWE files repair issues, GitOps links deploys.
   - **`knowledge`** — default adapters **Confluence · Obsidian · Wikis** (MediaWiki/etc.). Where operators/agents read & write project knowledge: runbooks + postmortems published, design notes, and the generation pipeline reads docs as **material/oracle** inputs ([ADR-0010](03-data-plane.md#adr-0010)). *Distinct from gbrain (dev-time agent memory).*

   Both reuse the **`notify`/receiver-port pattern** ([ADR-0059](03-data-plane.md#adr-0059) — one port, swappable adapters, secretless, policy-gated); operator writes ride `crew.ActionApplied` + `policy.Decided` ([Plan 40](../operators-sre.md#plan-40)/[Plan 29](../contracts-policy-flags.md#plan-29)). They join the enumerated patchability seams ([ADR-0057](#adr-0057)); full surface/events are a later round.
5. **No new event families.** Auth rides `user.*`/`session.*` ([ADR-0038](02-identity-security.md#adr-0038)); artifact pulls/publishes ride `exec.*`/`pipeline.*` ([Plan 11](../data-plane.md#plan-11)) with provenance on the artifact; tracker/knowledge writes ride `crew.*`/`policy.Decided`.

### Consequences
- **(+)** The meta-cloud's external touchpoints are uniformly swappable and user-controlled (register WorkOS *or* Entra, npm *and* an internal mirror, JIRA *or* Linear — HoBo routes among only what you registered, no app-code change, auto-fillable gaps), reusing the `auth` port, the `notify`/receiver pattern, secretless brokering, Matching/Dispatcher, air-gap mirroring, and SLSA/generation pipeline (net-new is a `hobo:artifact-repo` port + two named seams, no new events) while keeping the scope cut honest.
- **(−)** Each registered adapter is a maintained, conformance-covered surface (breadth bounded by conformance + AI generation, not free), and issue-tracker + knowledge leave their event/surface detail for a later round — a deliberate gap `hobo doctor` can flag.

## ADR-0075
**Interface stability tiers + a statically-evaluable provider Capability Spec (with the preview `wasi:websocket`).**

### Context
HoBo prefers standard `wasi:*` interfaces and authors `hobo:*` only for gaps ([Plan 20](../wasm-runtime-wit.md#plan-20)), pins exact `namespace:package@semver` versions, and absorbs upstream draft churn behind pins + compat shims ([Plan 20](../wasm-runtime-wit.md#plan-20)/[ADR-0024](#adr-0024)). It already has a **Capability Manifest** ([ADR-0009](02-identity-security.md#adr-0009): `capabilities/auth/cost.json` signs) and **static, compile-time capability feedback** ([ADR-0033](01-architecture-core.md#adr-0033) §6: an unsupported capability is flagged at author time with a remediation). Two gaps: (1) **WebSockets** are listed as a building block ([Plan 20](../wasm-runtime-wit.md#plan-20)) via a HoBo-authored `hobo:websocket`, but the *standard* `wasi:websocket` doesn't exist — WASI standardizes per-protocol sockets-family modules independently and 0.3 adds native async, so a websocket interface will most likely be a `wasi:`-namespaced, sockets-family interface over `wasi:io` streams; HoBo needs a preview now without forking from that future. (2) The Capability Manifest declares capabilities too coarsely to **statically determine availability of a specific `interface@version` and its stability** — exactly what a preview interface needs ("is `wasi:websocket@preview` available on a registered provider, and is it safe for prod?").

### Decision
1. **Every WIT interface carries a stability tier.** `stable · preview · experimental · deprecated`, declared alongside its `namespace:package@semver` (the tier enum lives normatively with the version policy in [Plan 20](../wasm-runtime-wit.md#plan-20)). `preview` = tracks an expected-but-unratified standard; `experimental` = HoBo-incubated, may be withdrawn; `deprecated` = scheduled for removal. Tier + version are recorded in the **manifest IR** ([Plan 21](../authoring-resources-wiring.md#plan-21)) per import/export. **The pin/upcaster/migration mechanics are not re-described here — they are [ADR-0024](#adr-0024) §5's versioning machinery**; a tier just selects how aggressively it applies (a `preview` bump may break; see the consumer contract in point 6).
2. **A preview `wasi:websocket` is the core websocket interface; `hobo:websocket` shrinks to a thin extension.** HoBo vendors + pins **`wasi:websocket@0.0.x-draft`** (`preview`), modeled on the WASI **sockets-family** shape over **`wasi:io` streams** (0.3-async-ready), with server-accept (via `wasi:http` connection upgrade) + client-connect exchanging messages over input/output streams. `hobo:websocket` is reduced to the HoBo-specifics the bare interface won't carry — **principal/`ctx.user` binding** ([ADR-0038](02-identity-security.md#adr-0038)), **`.allow()` verbs** (`accept`/`connect`/`send`/`broadcast`/`subscribe`), connection **addressing + channel fan-out** (`send-to`/`join`/`broadcast`), and **event-sourced connection lifecycle** (the **`ws.*`** family — `Connected`/`Authenticated`/`Subscribed`/`Unsubscribed`/`Disconnected`, [Plan 11](../data-plane.md#plan-11); per-frame messages ride the Streamer, not the log). The fuller interface reference is in [Plan 20](../wasm-runtime-wit.md#plan-20). Each ships a `@hobo/conformance` suite ([Plan 9](../generated-stack.md#plan-09)). When the real `wasi:websocket` is ratified, HoBo tracks it and migrates via the existing **upcaster/compat-shim** ([ADR-0024](#adr-0024)) — apps don't rewrite.
3. **The provider Capability Spec is the statically-evaluable declaration of implemented `interface@version@stability`.** The Capability Manifest's `capabilities` ([ADR-0009](02-identity-security.md#adr-0009)) is formalized to list, per provider, the **exact WIT `interface@semver` it implements, each with its stability tier and the `@hobo/conformance` suite version it passed** (+ the existing capability hints/`cost.json`). This is the spec HoBo "leverages to statically determine if things are available."
4. **Static availability resolution at author/compile time** ([ADR-0033](01-architecture-core.md#adr-0033) §6). Against the registered providers' Capability Specs, the SDK/Matching resolve each used interface: **available `stable`** → ok; **available only via `preview`/`experimental`** → a **compile-time warning** ("pinned, may change") surfaced through codegen ([ADR-0037](01-architecture-core.md#adr-0037)) + `hobo doctor`; **unavailable** → a **compile-time error + remediation** (use a registered provider that implements it, or auto-generate the adapter, [Plan 23](../generated-stack.md#plan-23)) — backed by the hard deploy-path `require`-miss `deployment.PlanRejected` ([ADR-0033](01-architecture-core.md#adr-0033)). Determinism is unchanged: this is a pure function of the catalog snapshot.
5. **Stability is governable** ([ADR-0074](02-identity-security.md#adr-0074)). An org may set a **mandatory policy rule (deny-ceiling)** — e.g. *"no `preview`/`experimental` interfaces in prod"* — turning the advisory warning into a hard, audited deny at `can-deploy`; absent such a rule, preview usage is advisory (warn, don't block). The websocket preview is thus usable today, and lockable by orgs that require only `stable` interfaces in production. **So self-host parity is about features + code, not auto-enforced posture** ([ADR-0024](#adr-0024) §6): both topologies ship the *same* deny-ceiling capability, but a hosted operator typically enforces "no-preview-in-prod" while a self-hosting org that never sets it runs preview in prod — a weaker posture by *choice*, not a silently-weakened build. To keep the [ADR-0024](#adr-0024) §6 "must not silently weaken self-host security" intent, the **safety-relevant deny-ceilings (no-preview-in-prod ceiling, min-provenance-tier) ship default-on in the hardened/`prod` Yard profile** and turning them *off* is the audited, explicit act — so a default self-host prod install is not silently less safe than hosted.
6. **Capability Spec accuracy is *continuous*, and a `preview` bump has a consumer contract.** Conformance gates at **publish** time, but a provider can **regress after publish** (drop/break an interface it still declares). So a Capability Spec is **periodically re-verified** (tie to the [Plan 12](../security-networking.md#plan-12) continuous-scanning loop): a regressed spec is treated **like a newly-disclosed CVE** — it follows the **decided yank lifecycle** ([ADR-0062](#adr-0062) §6: block the next dependent deploy + flag installed Sets + raise a critical-severity remediation obligation), rather than being trusted from a stale author-time snapshot. And because `preview` interfaces *can* break on a version bump, the **consumer contract is explicit and reconciled with pin-immutability** ([ADR-0024](#adr-0024) §5): a Bindle's interface pins are immutable **for that Bindle version**, so a breaking `preview` bump does **not** mutate a deployed Bindle in place — it ships a **mandatory upcaster** + a **deprecation window**, and the migration is realized as a **new Bindle version** (re-plan + re-conformance) that adopts the bumped pin. At deprecation-window expiry the old pin becomes **unservable**, so a still-deployed old-version Bindle is **blocked from redeploy** (and flagged for upgrade), not force-rewritten — pinned consumers (incl. everyone on the advisory-default websocket) get a gated migration path, not a surprise break and not an immortal pin.

### Consequences
- **(+)** WebSockets are supported now via a preview that aligns with the likely-ratified `wasi:websocket` (clean upcaster migration, no app rewrite, honestly labeled), and "is capability X available?" is answerable **statically, before deploy**, for any interface — reusing the Capability Manifest, static feedback, versioning/conformance, and codegen (net-new is a stability tier per interface + the `interface@version@stability` precision in the manifest) and composing with org governance.
- **(−)** Every interface carries a maintained stability tier + per-version conformance suite (a mislabeled tier misleads the static check), a `preview` interface can break on a version bump (HoBo ships the upcaster + bumps the pin), and Capability-Spec accuracy depends on providers declaring truthfully — conformance ([Plan 9](../generated-stack.md#plan-09)) is the check.

## ADR-0019
**Primary ICP — the indie developer and the agent acting on their behalf.**

HoBo serves four personas — application developers, platform engineers, operators, and AI agents-as-users ([vision.md#plan-00](../vision.md#plan-00), [ai-native-agent-auth.md#plan-06](../ai-native-agent-auth.md#plan-06)). The **primary ICP is co-primary: the indie/startup developer authoring a Bindle and the AI agent that deploys and operates it via MCP** — so every capability is reachable by both **SDK/CLI and MCP**, with first-class agent identity. The **platform engineer** (Resource Definitions, mapping rules, policy/cost rules — [25](../platform-engineering.md#plan-25)/[30](../contracts-policy-flags.md#plan-29)) and the **multi-tenant hosted operator** are first-class as well; the org-governance mechanism the operator needs — RBAC + mandatory policy rules (deny-ceilings) over HoBo's own control-plane surface — is [ADR-0074](02-identity-security.md#adr-0074) (the *hosted-operator-as-a-business* stays cut, [ADR-0064](#adr-0064)).

## ADR-0021
**NFR / SLO targets.** Proposed — numbers are defaults to ratify, not contractual SLAs.

[reliability-observability-cost.md#plan-05](../reliability-observability-cost.md#plan-05) lists HA targets and [verification](../generated-stack.md#plan-09) needs **measurable** thresholds. These are the targets, each with a verification method:

| Dimension | Target | Verified by |
|---|---|---|
| Time-to-first-deploy (scaffold → running on real cloud) | ≤ 10 min p50 on the happy path | E2E timing test |
| Local dev start (`hobo dev`, no cloud) | ≤ 60 s | [developer-experience.md#plan-07](../developer-experience.md#plan-07); integration test |
| Zero-secret rate (provider access via brokered/federated tokens) | ≥ 99% of provider calls; static keys only via explicit legacy escape hatch | [06](../ai-native-agent-auth.md#plan-06)/[12](../security-networking.md#plan-12); **gated:** a CI/`can-deploy` gate fails when the measured zero-secret rate over the conformance fixture run drops below 99% (the `token.*` audit feeds it) |
| Portability ("same Bindle, N clouds" unedited) | ≥ 2 providers for the reference app, design target N | [04](../control-plane.md#plan-04); **gated:** `multi-cloud-shop` E2E + the [ADR-0024](#adr-0024) §1 empty/satisfied-non-portable-surface assertion |
| Control-plane availability | 99.9% single-region / 99.95% multi-region | [05](../reliability-observability-cost.md#plan-05); **observed via** a fault-injection/SLO soak ([ADR-0047](02-identity-security.md#adr-0047)), not a per-deploy gate |
| Deploy resume after node loss | < 30 s (lease TTL + tail replay) | [05](../reliability-observability-cost.md#plan-05); chaos test |
| RPO | ~0 (sync quorum) / ≤ 5 s (async tier) | [05](../reliability-observability-cost.md#plan-05); **verified by** a DR-replay/chaos test measuring the actual data-loss window |
| RTO (full Yard rebuild from log) | < 15 min | [05](../reliability-observability-cost.md#plan-05); DR replay test |
| Plan-time cost estimate accuracy | within ±20% of a known fixture | [16](../reliability-observability-cost.md#plan-05); cost fixture test |
| Determinism | `replay == live state` for every durable run (hard invariant) | [09](../generated-stack.md#plan-09); determinism test |

**Determinism and zero-secret are hard invariants**, not best-effort. The table distinguishes **gated** dimensions (a CI/`can-deploy` gate blocks on a miss: zero-secret, portability, determinism) from **observed** dimensions (measured by a soak/DR test, not blocked per-deploy: availability, RPO/RTO, cost accuracy) — so the verification column states enforcement honestly. Some numbers (availability, cost accuracy) are measurable only once multi-region HA and the full cost model exist; until then they are verified on representative-but-partial setups.

## ADR-0063
**Scope is the whole designed surface; sequencing and phasing are deferred.**

Everything in the suite ([Plan 0](../vision.md#plan-00)–[Plan 46](../governance-planes.md#plan-46)) is **in scope**, bounded only by [ADR-0064](#adr-0064). There is **no version ladder and no deferred-feature bucket in the design**: the generation pipeline, multi-region HA, FinOps showback, the full dashboard, platform-engineering depth, the Operator Crew, the generated stack (infrastructure **and** app/UI), patchability, SRE/incident management, the governance planes (compliance enforcement, AI safety), the `notify` port, and Registry distribution are all part of the designed surface. They ride existing machinery (ports, policy, events, conformance) with no new runtime.

**Build sequencing and delivery phasing are deferred planning** (archived, `archive/roadmap.md`) — to be scoped later, not part of the current design state. The only architectural anti-goals are positioning, not deferrals: HoBo **composes** IaC engines (Pulumi/Terraform/OpenTofu/Crossplane) via the IaC port rather than replacing them ([Plan 4](../control-plane.md#plan-04)); it is not a standalone secret-management product or a generic app framework ([vision non-goals](../vision.md#plan-00)).

## ADR-0064
**Scope: AI-native meta-cloud (remove business/monetization; keep app generation).**

### Context
HoBo is an **AI-native meta-cloud** — a direct competitor to **Convex, Lakebed.dev, and Nitric**: a portable durable runtime + a cloud-agnostic provisioning control plane that any cloud's primitives plug into via ports, operable by agents, with the **generation pipeline** generating the missing adapters. The one kind of scope that drifts past a meta-cloud is **SaaS-business functions** — billing, subscriptions, invoicing, tax/VAT, chargeback, monetization, rev-share. HoBo is not a payments/billing product, and a meta-cloud should not carry a commercial toolkit.

### Decision
**Scope HoBo to the meta-cloud, minus money-movement.** The test for a capability: ***would Convex, Nitric, or Lakebed ship this as a platform capability?*** *developer-facing ≠ out of scope* — these competitors are batteries-included; the cut line is **business/monetization**, not "non-developer" and not app generation.

1. **Keep** (in scope): cloud/infra orchestration; the durable, event-sourced runtime; AI-native agents + MCP; the **generation pipeline** (AI-generated providers/adapters/implementations behind ports) and self-optimizing runtime functions (`"use training"`); the developer-facing **cloud primitives** (data, reactivity, auth, search, messaging, storage) as ports; and **app generation** — the **UX Designer** operator, **design.md** as a required input, **OpenUI**, **json-render**, and **mcp-apps**, plus the app/UI layer of the generated stack and the `ui-render` port ([ADR-0055](03-data-plane.md#adr-0055)/[ADR-0056](03-data-plane.md#adr-0056)). Cloud-cost **FinOps** (estimates/budgets/showback/quotas/spend-safety) stays — it is infra, not money.
2. **Remove — business/monetization only:** the `billing` port / chargeback / invoicing / tax / rev-share / subscriptions; the marketplace's monetize lifecycle. ADR-0039 is **Metering, quota & cost attribution** (FinOps only).
3. **Consolidate:** `notify` (email/sms/push/webhook) is a thin **cloud-messaging port** in the resource catalog, not a standalone plane; the marketplace's publish/discover/install/trust folds into the **Registry** + **Resource Packs**; governance planes (compliance, AI safety) keep their **enforcement** machinery.

### Consequences
- **(+)** Sharp, defensible identity: agnostic IfC + durable event-sourced runtime + agents/generation pipeline + conformance + patchability + **app generation**; only the business sprawl leaves.
- **(+)** Clear competitive story vs Convex/Lakebed/Nitric; no first-party commercial toolkit to maintain (commercialization is out of design scope).
- **(↔)** Money-movement terms are removed across the suite; metering/showback/quota/spend-safety (FinOps) and the app-generation stack (UX Designer/design.md/OpenUI/json-render/mcp-apps/`ui-render`) stay.
