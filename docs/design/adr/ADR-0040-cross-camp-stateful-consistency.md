# ADR-0040 — Cross-Camp stateful consistency

- **Status:** Accepted
- **Date:** 2026-06-22

- **Origin:** open question #16, explicitly left as a follow-up by [ADR-0028](./ADR-0028-multi-camp-deployment-model.md), and the dependency Plan 32 / Plan 34 / [ADR-0035](./ADR-0035-custom-domains-and-multi-cloud-ingress.md) deferred their cross-Camp cases to. Designed via brainstorming + grill-with-docs.

## Context
[ADR-0028](./ADR-0028-multi-camp-deployment-model.md) made a Bindle deployable to **1..N Camps** (multi-cloud), with cross-Camp `bind` edges Yard-wired and the data plane talking directly — but explicitly deferred **stateful-data consistency across Camps**. The question: when a Bindle spans clouds, is cross-Camp state a HoBo *guarantee* (cross-cloud event replication) or an *app responsibility* (eventual)? It can't be silently strong — cross-provider quorum writes are high-latency and partition-prone (CAP). And it's load-bearing: Plan 32 deferred cross-Camp reactive queries, Plan 34 deferred cross-engine/CDC moves, and [ADR-0035](./ADR-0035-custom-domains-and-multi-cloud-ingress.md) routes traffic across Camps — all waiting on this.

## Decision
1. **Cross-Camp state declares a replication topology; HoBo wires it and surfaces the guarantee — no silent strong consistency.** Per piece of cross-Camp state, the topology is one of: **single-writer-Camp** (one Camp owns the data; other Camps read — the **default**), **active-active-eventual** (CRDT / event-merge, opt-in), or **pinned-single-Camp** (data lives in one Camp; compute may still span). The topology is part of the resource's resolved config / Resource Definition ([Plan 26](../26-environments-deltas.md)/[Plan 25](../25-resource-definitions-matching.md)), not app code.
2. **The event log is the cross-Camp replication backbone.** HoBo-native event-sourced state (actors, runs, projections) replicates **via the log**: the owning Camp is the single writer; other Camps consume a **replicated read-stream** into **bounded-staleness projections** (reusing event-store replication, [Plan 11](../11-event-model.md), and the quorum/HA machinery, [Plan 5](../05-reliability-ha.md)). **Provider-backed stores** (`sql`/`kv`/`bucket`) default to **single-writer-Camp + cross-Camp read** over the connectivity tiers ([Plan 13](../13-networking-connectivity.md)); **active-active CDC / multi-primary for provider stores is deferred** — the same boundary [Plan 34](../34-app-data-migrations.md) drew for cross-engine/CDC moves.
3. **Consistency is surfaced honestly.** Reads from a non-owner Camp are **labeled bounded-staleness** (stale-by ≤ replication lag, reusing [Plan 5](../05-reliability-ha.md) §Control-plane-HA's labeled reads) — never silently stale. **Reads-your-writes** holds within the writer Camp (and cross-Camp after replication, observable via the stream `seq`/version). **Consistency-requiring writes "go home"** — they route to the owning Camp. **Cross-Camp reactive queries** ([Plan 32](../32-reactive-live-queries.md)'s deferred case) subscribe to the owner Camp's reactor or a replicated-stream reactor that carries the staleness label.
4. **No new event types** — replication rides the existing event-store replication ([Plan 11](../11-event-model.md)/[Plan 5](../05-reliability-ha.md)); a topology is resource config; staleness is a read-label + an observability signal ([Plan 14](../14-observability.md)) that can trip a policy obligation ([Plan 30](../30-policy-plane.md)) when lag exceeds a bound.

## Alternatives considered
- **HoBo guarantees strong cross-cloud consistency (quorum event replication across clouds).** Rejected: high-latency + partition-prone across providers; makes a multi-cloud Bindle slow by default and over-promises against CAP. (Strong consistency *within* a Camp is unchanged — that's the runtime backend's quorum.)
- **Purely app-owned (HoBo only wires connectivity).** Rejected: abandons the multi-cloud-data promise and gives developers no patterns — the gap #16 exists to close.
- **Provider-native multi-region storage replication.** Rejected as the mechanism: provider-specific (breaks agnostic) and doesn't span *different* providers (the actual cross-Camp case). It can still realize a single-Camp's HA underneath.
- **A HoBo-managed global state store.** Rejected: puts HoBo on the data-plane request path (latency/cost/SPOF), contradicting [ADR-0028](./ADR-0028-multi-camp-deployment-model.md) ("the Yard is never on the request path").
- **Active-active CDC for provider stores in v1.** Rejected for v1 (kept as the opt-in `active-active-eventual` direction): heavy per-engine CDC + conflict handling, mirroring [Plan 34](../34-app-data-migrations.md)'s deferral.

## Consequences
- **(+)** Resolves the keystone #16 and unblocks the deferred cross-Camp cases in [Plan 32](../32-reactive-live-queries.md) (reactive), [Plan 34](../34-app-data-migrations.md) (data move), and [ADR-0035](./ADR-0035-custom-domains-and-multi-cloud-ingress.md) (ingress) — multi-cloud now has an honest *data* story.
- **(+)** Reuses event-sourcing as the replication backbone, the Plan 5 quorum + labeled-staleness machinery, and the connectivity tiers — minimal new mechanism (a declared topology + a read label + a write-goes-home rule).
- **(+)** CAP-honest: developers see the real guarantee (bounded staleness, single-writer) and choose active-active-eventual deliberately where they can tolerate merge semantics.
- **(−)** Single-writer-Camp means the owning Camp is a write bottleneck/availability dependency for that state (mitigated by the owner Camp's own intra-Camp HA, [Plan 5](../05-reliability-ha.md)).
- **(−)** Active-active-eventual requires CRDT/merge modeling by the developer; HoBo provides the plumbing + event-merge, not automatic conflict resolution for arbitrary data.
- **(−)** Provider-store active-active/CDC remains deferred, so some cross-cloud data patterns stay single-writer or app-handled for now.
